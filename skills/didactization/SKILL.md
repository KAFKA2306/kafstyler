# 知見の教材化と推敲

didactization は、根拠がある知見を他者が理解・再現・応用できる説明へ変える工程。この名称はKafstyler内の役割を指し、**独立した査読を実施していない内容を査読済みと呼ばない。**

記事・研究ノートには[知見の教材化](#発見を汎用原則に変える)を、README・PR・UI文言・障害報告・運用報告には[意味を保つ推敲](#本文の推敲と提出前の確認)を適用する。後者に独自の発見を要求しない。両方とも自然な日本語を守り、知識を創作して埋めない。

[発見と原則](#発見を汎用原則に変える) · [記事の構成](#記事を読者から設計する) · [見出しと用語](#タイトル見出し用語の見直し) · [本文と提出前の確認](#本文の推敲と提出前の確認)

[imozの執筆・推敲ルール](../../BIBLES.md#imozの日本語編集)を読み、読者、用途、媒体、変更範囲、原資料を確かめる。[出力の共通基準](../../MISSION.md)

## 発見を汎用原則に変える

**教材の中心は、根拠のある汎用原則。** 文献の寄せ集めやもっともらしい一般論だけで新規記事を作らない。[記事と自己検証の原典](../../BIBLES.md#知見を残す記事の基準)

1. **観測と出典を固定する。** 実験、失敗、一次資料との不一致、公開後の利用結果から発見候補を特定する。対象、入力、環境、版、観測結果、一次URLを残す。AIの着想を実測と混同しない。
2. **汎用原則を導く。** 「どんな条件で、何をすると、何を防げる／改善できるか」を一文で記す。観測事実、解釈、仮説を分け、観測から一般化できない範囲を明記する。
3. **反例と境界を付ける。** 成功例だけでなく失敗例、比較対象、適用外の条件を示す。必要な場合は [disprove](../disprove/SKILL.md) で前提を検証し、[adjudicate](../adjudicate/SKILL.md) で比較する。実験や査読を行わなければ未実施とする。
4. **第三者が試せる形にする。** 必要な前提、具体的な入力・操作・期待される結果、失敗時の観測点を示す。例えば二重登録の対策なら、同じイベントIDを2回送り、登録件数を確認する手順と、IDが変わると成立しない条件を書く。この例は説明用であり、実測の証拠ではない。
5. **公開先を選ぶ。** 独自の発見と根拠があり、既存記事に統合すると読者の用事を損なう場合だけ新規記事にする。それ以外は既存記事を修正・統合し、重複と根拠のない文章を削る。訂正と来歴は正本に残す。

完成条件は、読者が原則の成立条件を説明し、再現手順をたどり、反例で適用を中止する判断ができること。確認できない効果を保証しない。

## 記事を読者から設計する

前節で原則・反例・公開方針を決めたうえで、読者の疑問から操作と判断までを組み立てる。[読者中心の構成](../../BIBLES.md#読者から記事を設計する)

1. 読者が何を知りたくて読み、最後に何を判断・操作するかを依頼や利用記録で確認する。根拠のない読者像は仮定とする。
2. タイトル・導入・見出しだけを並べ、「問い → 原則 → 根拠 → 再現例 → 反例・適用限界 → 次の操作」のうち必要な項目を順に説明する。読者の用事に不要な節を増やさない。
3. 既知の知識を説明する入門・案内・手順書に「独創的な発見」を要求しない。教科書風の体裁を成果と数えず、読者が使える説明か確かめる。

## 技術白書を構成する

技術白書は、技術上の問題、選択肢、評価結果を示し、読者が採否を判断するための文書。[白書の構成と技術報告の原典](../../BIBLES.md#技術白書の執筆)を使い、論文の体裁や宣伝文句を目的にしない。

1. 読者が決めること、対象技術と版、検討範囲を定め、最初に結論と主要な根拠を要約する。
2. 問題、原因、採否基準、技術的な仕組み、比較する代替案を説明する。選択肢を推奨する場合は、他案より適する条件を明確にする。
3. 重要な主張は一次URLか実測結果に結び付ける。測定を使うなら入力、環境、版、方法、比較条件、結果を残し、再検証できるようにする。
4. 推奨に不利な結果、制約、未確認事項を示す。事実・推測・予測を区別し、独立した査読や評価を実施していなければ実施済みと書かない。
5. 節の名前や数を固定せず、根拠のない節と重複を削る。完成条件は、読者が提示された証拠から選択肢の採否と適用条件を判断できること。

## タイトル・見出し・用語の見直し

1. 見出しだけで問いと答えの場所が分かるか確認する。同じ階層は詳しさと文型をそろえる。本文を先に読む必要がある抽象的な見出しは直す。
2. 専門語の意味と範囲を原典で確認し、同じ概念には同じ語を使う。異なる工程は書き分け、珍しい語を意味のない装飾に使わない。必要な説明は初出に添える。
3. 変更するタイトルと見出しに代案を一つ作り、元の本文と前後の文脈を含めて比較する。正式名称・引用・識別子は原文どおりに保つ。名称やパスを変えるときは目次と参照先も更新する。

## 本文の推敲と提出前の確認

1. **原意を守る。** 原資料を読み、主張、数値、時点、条件、不確実性、引用、出典との対応を固定する。推測を事実へ格上げせず、断定を強めない。説明の飛躍、曖昧な評価、不要な重複を削る。
2. **自然で読みやすく直す。** 必要なら [yomiyasu](../../BIBLES.md#成果物の根拠と読みやすさ) を参照し、読者に合う語順、具体的な動詞、結論と根拠の位置、文章の長さを整える。AI特有の定型句、過剰な列挙、同じ内容の反復を削る。原意を変える言い換えはしない。PR・UI・報告ではこれを中心とする。
   - README・製品紹介・初回導線では、用途の限定、試用前の注意、形式的な確認リスト、一般的な免責文を入れない。既存の該当表現も削る。価値・実例・最初の操作を先に書き、不要な強調を外す。動作に不可欠な前提は操作の箇所で説明し、実測していない成果は断定しない。
3. **画面と操作を確認する。** UIは[判断の表示基準](../../BIBLES.md#かふかのデザインパターン)と照合し、状態、根拠、操作ラベルから次の行動を選べるか確かめる。美文より操作可能性を優先する。
4. **読者の入口で試す。** 推敲後の内容と原資料を照合し、手順書なら実際に操作し、記事なら根拠・再現手順・境界条件をたどる。必要な未確認事項と再開条件は既存記録に残す。[成果物の確認手順](../../AGENTS.md)
   - 定期・イベント実行の報告では、作業台帳の実績、失敗、古い状態を分け、最終確認時刻と必要な操作を伝える。差分のない回は既定の通知条件に従う。[常駐運用](../autocatalyze/SKILL.md#常駐エージェントと定期実行)

重要な主張や数値を変更したら原典と照合し、必要なら [disprove](../disprove/SKILL.md) で反例を探す。未実施の査読・実験を実施済みと書かない。本文、見出し、リンクの差分を読み直す。

改稿稿と参照先を依頼者または呼び出し元に返す。重要な根拠と採否理由は既存の記録に残す。

## Mermaid図解

説明する対象に工程・分岐・状態遷移・依存関係がある場合は、[共通規約のMermaid図解](../../AGENTS.md#mermaid図解)に従い、文章と対応するMermaid図を含める。図のノードと矢印は観測・原典・実装に合わせ、推測の経路を事実と混同しない。図を使わないほうが明瞭な単純な文章に装飾的な図は足さない。
