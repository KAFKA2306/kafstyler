## 設計前に評価を決める

**自己採点だけで合格にしない。** 文書・PRの件数や実装者が変更したテストだけでは成果を示せない。利用者の最終操作、外部の正本、着手前に固定した失敗例、独立した評価入力で確かめる。独立評価できない条件は未確認として[指標の抜け道](../../BIBLES.md#評価指標のすり替えと独立した検証)を調べる。

`disprove` から反例の測定を頼まれた場合は、その測定結果を呼び出し元へ返す。成果物の正式な評価条件は、`reconceptualize` で完成場面を確かめた後に固定する。

1. **失敗を見分ける。** [目標設定](../reconceptualize/SKILL.md)で決めた利用者の用事と観測する結果から、重大な失敗を見分ける評価を作る。対象分野の公式仕様、外部の実践例、必要な数理モデルと今月の関連研究を調べ、採用した原典のURL、版または公開日、使う判断を残す。同じ用事・仕様・判定条件の確認済み資料は再利用する。関連研究が見つからなければ検索範囲を残し、合否に必要な根拠を確認できなければ該当項目を未確認にする。
2. **入力と合格値を決める。** 必須項目ごとに、利用者の入口、代表入力と重大な失敗例、最後に観測する結果、計測方法と単位、合格値、実行コマンドや採点手順を作業台帳にまとめる。比較では基準版、環境、許容差も定める。データの粒度や識別子が合否を左右する場合は、既存の正本と代表データを `canonicalize` の現状調査で確認して期待値を決める。小さな変更では失敗を見分ける既存の検証を使う。
3. **判定方法を選ぶ。** 機械的な照合、既存テスト、結果の読み戻しを優先する。定性的な判断が必須なら、観察可能な採点基準と合格・不合格の例を用意し、成果物を作ったエージェントから独立した自動採点を使う。モデルで採点する場合はモデルID、採点手順、合格値と判定が割れた場合の扱いも固定する。採点の調整に使った例と最終確認に使う例を分け、採点時は候補の由来と実装者の自己採点を渡さない。
4. **反例で確かめて固定する。** 評価条件を確定する前に [共通の連携手順](../../AGENTS.md#コマンドの連携)に従って [反証レビュー](../disprove/SKILL.md) を呼ぶ。入力、合格条件、既知の不合格例を渡し、欠陥があっても合格する反例を探す。新しい判定は、着手前版や検証用の例で合格例を通し、不合格例を落とす。対象の設計案・初稿・実装を作る前に評価条件と実行方法を固定する。評価だけの依頼では測定前に固定する。必須項目で判定方法が決まっていなければ、判定手段の調査を続け、設計着手は保留する。
5. **既存の検証につなぐ。** 対象に既存の検証コマンドや配布ゲートがあれば、適用できる必須判定をそこにつなぐ。候補の実装・制作から評価条件と期待値を独立させ、結果に合わせて合格条件を緩めることを禁止する。要件の変更や測定の誤りで評価を改める場合は、理由と新旧の評価版を記録し、同じ新条件で比較対象と候補を測り直す。

## 固定した評価で採否を決める

1. **提出版を測る。** 普段の利用経路から提出する版の実物を動かし、先に固定した条件で各必須項目を自動判定する。採点が割れた場合、証拠が足りない場合、必須の判定を実行できない場合は未確認にする。ばらつきが採否を左右する場合は、着手前に定めた回数と集計方法で測る。
2. **合否と再実行方法を残す。** 各必須項目の合否、対象と評価条件の版、再実行方法、観測結果を記録する。全必須項目が合格すれば、品質判定のための人手レビュー待ちを作らず完了する。不合格や未確認が一つでも残れば、採用・完了の判定は保留する。公開や権限などに必要な承認は対象の規約に従う。
3. **不合格を直して再評価する。** 不合格を直せる範囲では修正し、同じ入力と影響を受ける既存の確認をやり直す。再実行できない場合は、得られた結果と再開条件を残す。改善は必須条件を満たし、重大な退行がなく、固定した指標が比較基準より良くなった場合に認める。

報告書や読者向けブリーフの作成まで依頼されている場合は、[`kafstyler:didactization`](../didactization/SKILL.md) を呼ぶ。原稿、読者、測定値、合否、未確認事項を渡し、推敲した報告を返す。

呼び出し元がある場合は、合否と測定結果を元の作業へ返す。

### 成果物に合う判定を選ぶ

| 対象 | 観測する結果の例 |
| --- | --- |
| 画面 | 主要操作後の表示・保存状態、固定環境での見た目の差分 |
| API・CLI | 代表入力と境界入力に対する返答、保存結果、エラー時の状態 |
| データ・集計 | 原資料と突合した件数・合計、重複・欠損・参照整合性 |
| 文書・調査 | 読者の確認質問に対する答えと根拠箇所、出典への到達、記載手順の実行結果 |
| 画像・音声・3D | ファイルを開けること、用途に必要な寸法・尺・形式、参照例に基づく品質基準 |
| 定期処理 | 通常起動から届く結果、再送・並行実行後の重複件数と再開位置 |

## 画面の評価

普段の入口で評価対象の版を表示し、変更が影響する画面幅、入力方法、状態で主要な操作を最後まで試す。[かふかのデザインパターン](../../BIBLES.md#かふかのデザインパターン)の画面評価ガイドを使う。

見た目の改善を頼まれた場合や、変更が情報の並び、操作の見つけやすさ、文字の読みやすさに影響する場合は、設計前に見た目の合格条件、参照例、画面幅、許容差を固定する。変更が効く箇所の前後を同じ条件で撮影し、見た目と操作をそれぞれ判定する。前後の画像と対象版を添える。比較できなければ、見た目は未確認と記す。初見での見つけやすさが必須なら、候補を作った担当から独立したブラウザの試行に目的だけを渡し、到達結果を判定する。

## 検証手順の評価

[Claude Codeチームの検証原則](../../BIBLES.md#claude-codeの検証)に沿って、変わる範囲から評価方法を選ぶ。

- 機能の検証では実際の入口から最後の結果まで観測する。全入力で守る条件は、往復変換や再実行などで守る性質を定め、境界を含む入力で試す。組み合わせを広く試す必要があれば既存の入力生成器を使い、失敗した入力を再実行できる形で残す。挙動を保つ置き換えでは、旧版と新版を同じ入力で動かし、空白など判定に関係しない差の扱いと許容する変更を先に決める。
- 判定手順を評価するときは、過去に問題が起きた版と安定していた版を使う。確認した事例数、見逃しと誤検知を記録する。繰り返し調整する評価では、調整に使う事例と最終判定に使う固定の事例を分ける。レビューのどの段階で指摘が落ちたかが判断に効く場合は段階ごとに数える。

## 定期実行と再開の評価

常時稼働エージェントでは、期限内に確認された実成果、重複反映0件、再開成功、重大障害の検出、不要なLLM呼出し・通知の減少を測る。起動成功だけでは新規成果と数えない。[運用中核](../autocatalyze/SKILL.md#常時稼働エージェントの中核)

[常駐エージェントの聖典](../../BIBLES.md#常駐エージェント)を参照し、[自律開発の実行手順](../autocatalyze/SKILL.md#常駐エージェントと定期実行)で選んだ入口と成果の正本を使う。[継続運用の合格条件](../reconceptualize/SKILL.md#継続運用の合格条件)に沿い、一周期の成果と運用全体をそれぞれ判定する。

実際に設定した定刻、イベント、再開の経路を使い、代表入力が変わる回、次に入力が変わらない回、中断して再開する回を順に観測する。イベントがない間に起動しない設計なら、合意した観測期間に余分な起動がないことを確認する。一周期では、通常起動から利用者が期限内に成果を確認できるかを判定する。運用全体では、その後も次の起動と再開が成立し、必要な成果が抜けず、余分な仕事が増えていないかを判定する。関連する失敗事例は次から選ぶ。

| 入力と条件 | 合格と分かる結果 |
| --- | --- |
| 代表入力が更新され、予定時刻またはイベントで起動する | 期待する成果と必要な通知が期限内に普段の入口へ届き、次の起動条件を確認できる。 |
| 取得に成功し、処理対象に差分がない | 変更なしと記録され、不要なLLM呼び出しや同じ内容の通知が発生しない。 |
| 書き込みが反映された直後に応答が途切れ、同じイベントを再送する | 状態を読み戻して再開し、成果と外部への書き込みが各1件のままになる。配信済みの通知は重ねず、必要な未配信分を一度届ける。 |
| 同じ正本を更新する次の実行が、前の実行中に起動する | 同時に書き込む実行が1件以下になる。待っていた実行は先行分を反映した状態から判断する。 |
| 作業を途中で止め、別セッションで同じ案件を開く | 最後に確認した成果と次の工程が分かり、未完了の工程から進められる。 |
| 起動受付の後に処理が失敗する、または必要な権限が拒否される | 成果確認済みにならず、必要な対応を追跡できる。回答が必要なら、回答後に同じ案件を再開できる。 |
| 予定の起動が発生しない、または必要な成果・通知が期限までに届かない | 予定時刻・イベントと実行・配布の記録を照合して未到達を検出し、最後の確認と再開条件が残る。 |

起動、実行、LLM呼び出し、通知、成果の読み戻しを、作業ID、起動を識別するイベントIDまたは予定時刻、実行IDで突き合わせる。入力と評価の版、最後の確認と次の起動条件も記録する。実行数、成果の件数、同じ入力や配布先に対する重複、未到達の件数、利用者の確認にかかった時間から、変更に効く指標を選ぶ。取得に失敗して差分を見られなかった回は変更なしとして数えない。起動経路を実際に試せない場合は、観測できなかった条件を運用全体の判定に残す。
