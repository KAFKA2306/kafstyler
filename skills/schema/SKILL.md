# データ設計

任意の出力で人が読む文章には[imozの執筆・推敲ルール](../../BIBLES.md#imozの日本語編集)を適用する。[出力の共通基準](../../MISSION.md#出力の共通基準)

1. 答える問い、現行データの管理者、実際の入力を確かめる。エンティティの識別子、関係、操作を定義する。産業分野の概念にはIOF、業務オブジェクトにはFoundryの設計を必要に応じて参照する。
2. 対象と粒度が同じデータについて、実装、設定、文書で有効な定義と、読み取り、書き込み、検証の入口を洗い出す。項目、型、識別子、制約を管理する正本を一つに決める。正本の場所、管理者、更新経路を明記する。
3. 検索、判断、検証に使う項目を選ぶ。必要に応じて出典ID、URL、時点、版、単位、欠損値の意味、来歴を持たせる。名前はプロジェクトで使われている語彙から選ぶ。
4. 台帳は一行のキー、状態遷移、訂正履歴を定め、再入力時の照合方法を決める。マスターは識別子、正とする属性、必要に応じて有効期間を定める。
5. 分析では最初にファクトの一行が表す粒度を定める。粒度ごとに集計し、結合後の件数増加、対応先のないキー、合計を確認する。
6. dbtを使う場合は `source()` と `ref()` で正本と派生モデルをつなぎ、必要な一意性、関係、突合の条件を検証する。
7. Obsidianノートには[frontmatterとタグの規約](../../BIBLES.md#ノートの管理)を適用し、想定したプロパティやタグで探せることを確認する。
8. [共通の連携手順](../../AGENTS.md#コマンドの連携)に従い、設計した契約を確定する前に [`kafstyler:scrutiny`](../scrutiny/SKILL.md) を呼ぶ。 識別子、粒度、正本、実データの例を渡す。重複、欠損、再入力、結合で誤った結果が出る例を調べ、指摘を契約と検証条件に反映する。 実装や移行も依頼され、既存の定義が競合する場合は、必要な項目、値、訂正履歴を正本へ移す。利用側を正本の参照または正本からの生成に切り替え、同じデータを独立して定義・更新している経路を廃止する。原資料は来歴として残し、集計、表示、互換形式は正本から作る。

## 人間の回答を待つ質問の台帳

依頼と許可の範囲で、設計、実装、検証、反映の各工程を自律で完了させる。自律実行の仕組みを設計するときも、以下の手順を入出力と状態遷移に組み込む。

1. 既存の指示、記録、許可、実データを確認し、許可された代替手段と可逆な既定値を検討する。それでも本人だけが持つ情報、権限者の判断、必須の許諾がなければ合格条件を満たせない場合に限り、質問を台帳に登録する。
2. 許可された永続的な保存先を台帳の正本にする。同じ役割の台帳があれば再利用する。一つの判断につき一件とし、対象と判断内容の組で質問を照合する。初回は登録し、再検出時は同じ行を更新する。質問ID、質問、回答者、回答が必要な根拠、確認した代替手段、止まる工程、再開条件、状態を記す。機密を含む項目は認可済みの非公開の場所で扱う。
3. 台帳に蓄積した未回答の質問は、依存しない工程を進めたうえで、必要なものをまとめて提示する。回答を待つのはその回答に依存する工程に限る。利用できる情報と道具で進められる残りの工程は、確認を挟まず自律で完了させる。
4. 次の実行で台帳を読み、未回答の質問と現在の再開条件を照合する。有効な回答を得たら回答の参照先を記して回答済みにし、該当工程を再開して検証する。条件が変わって回答が不要になったら、その根拠を記して解消する。必須の回答が残る工程は未完了として扱う。

## 完了条件

設計結果に正本と利用側の参照先を示す。設計のみの依頼で既存定義が競合している場合は、切り替え手順も示す。

自律実行の仕組みでは、回答なしで進む案件と回答が必須の案件を一件ずつ使い、前者が登録なしで完了し、後者は再実行でも同じ質問が一件にまとまり、回答と独立した工程は完了し、回答を記録すれば残りを再開できることを確かめる。

実装や移行を含む依頼では、対象ごとに現行の正本が1件、同じ役割を持つ独立した現行定義が0件であり、普段の読み取り、書き込み、検証が正本につながることを確認する。移行した場合は、前後の識別子、件数、必要な履歴を実レコードで突き合わせる。競合や未確認が残る間は統合完了とせず、残る箇所と再開条件を示す。

実データで検証できる場合は、[`kafstyler:benchmark`](../benchmark/SKILL.md) を呼ぶ。データの場所、設計した契約、正本と競合定義の件数、利用側の入口、一意性、参照整合性、期待件数を渡す。結果を設計に反映し、確認した契約と検証結果を示す。
