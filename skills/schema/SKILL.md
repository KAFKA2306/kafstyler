# データ設計

任意の出力で人が読む文章には[imozの執筆・推敲ルール](../../BIBLES.md#imozの日本語編集)を適用する。[出力の共通基準](../../MISSION.md#出力の共通基準)

1. 答える問い、現行データの管理者、実際の入力を確かめる。エンティティの識別子、関係、操作を定義する。産業分野の概念にはIOF、業務オブジェクトにはFoundryの設計を必要に応じて参照する。
2. 対象と粒度が同じデータについて、実装、設定、文書で有効な定義と、読み取り、書き込み、検証の入口を洗い出す。項目、型、識別子、制約を管理する正本を一つに決める。正本の場所、管理者、更新経路を明記する。
3. 検索、判断、検証に使う項目を選ぶ。必要に応じて出典ID、URL、時点、版、単位、欠損値の意味、来歴を持たせる。名前はプロジェクトで使われている語彙から選ぶ。KAFKA2306のWeb UIの表示契約を設計するときは、[かふかのデザインパターン](../../BIBLES.md#かふかのデザインパターン)のコンテンツスキーマを読み、実績、予測、仮説、未確認と出典を表示側へ渡す方法を決める。業務データの定義は対象プロジェクトの正本に置く。
4. 台帳は一行のキー、状態遷移、訂正履歴を定め、再入力時の照合方法を決める。マスターは識別子、正とする属性、必要に応じて有効期間を定める。
5. 分析では最初にファクトの一行が表す粒度を定める。粒度ごとに集計し、結合後の件数増加、対応先のないキー、合計を確認する。
6. dbtを使う場合は `source()` と `ref()` で正本と派生モデルをつなぎ、必要な一意性、関係、突合の条件を検証する。
7. 利用先を問わず、新規・既存のすべてのMarkdownに[frontmatterとタグの規約](../../BIBLES.md#ノートの管理)を適用する。README、規約、記事、スキルも対象に含め、既存の有効な値、独自キー、配布・公開先が必要とする型を保つ。想定したプロパティとタグで文書を探せることを確認する。Obsidianを使えない環境ではYAMLを解析して同じ条件で照合する。
8. [共通の連携手順](../../AGENTS.md#コマンドの連携)に従い、設計した契約を確定する前に [`kafstyler:scrutiny`](../scrutiny/SKILL.md) を呼ぶ。識別子、粒度、正本、実データの例を渡す。重複、欠損、再入力、結合で誤った結果が出る例を調べ、指摘を契約と検証条件に反映する。実装や移行も依頼され、既存の定義が競合する場合は、必要な項目、値、訂正履歴を正本へ移す。利用側を正本の参照または正本からの生成に切り替え、同じデータを独立して定義・更新している経路を廃止する。原資料は来歴として残し、集計、表示、互換形式は正本から作る。

## 台帳とObsidian Vaultで文書を整理する

散在・重複した文書の整理に使う。移行も依頼されたら、台帳に記した計画を実施して検証する。

1. 対象の保存場所と既存の目次・台帳を調べる。利用者が探す情報と普段の入口を決め、文書の用途、内容の重複、出典、参照元、配布や公開で固定されたパスを確かめる。
2. 既存の台帳を使い、なければ対象プロジェクト内に作る。文書ごとに既存のIDまたは最初に棚卸ししたパスをキーにし、元の場所、用途、正本のパス、処置とその根拠、状態を記す。再実行時はIDと元のパスに加え、移動後の正本のパスも照合する。同じ正本への移行元が複数ある場合も、元の行と根拠を残す。判断が残る文書は次に確かめる内容を記す。
3. 必要な情報と出典を正本に統合する。既存のVaultか、正本を含むプロジェクトのフォルダをObsidian Vaultとして開く。配布・公開先が使う固定パスは保ち、台帳からその正本へ案内する。文書を移したら、移した文書と参照元の相対リンクを更新する。旧版を片づける場合は [`kafstyler:prune`](../prune/SKILL.md) で参照元と移行結果を確かめる。
4. 台帳の行から正本と処置の根拠を読み戻し、READMEや目次から必要な文書と見出しを開く。Vaultのプロパティ・タグ検索で想定した文書が見つかることを確認し、同じ依頼で再実行して台帳と正本が重複しないことを確かめる。Obsidianを使えない環境ではYAMLと相対リンクを照合し、アプリでの確認状況を記録する。

## 定期実行と再開の記録

常駐エージェントの実装では、[作業台帳](../../AGENTS.md#作業台帳)や既存の実行履歴を使う。同じ目的を引き継ぐ作業ID、起動を識別するイベントIDまたは予定時刻、再試行を識別する実行IDを、区別できるようにする。予定時刻を使う場合はスケジュールと時間帯も識別できるようにする。

- 受付、実行中、回答待ち、失敗・中止、成果の確認済みを識別できる状態を定める。対象と入力の版、最後に確認した成果の参照先、次の工程を残す。長く使う判断は、根拠と適用条件を添えて既存の知識の正本に保存する。
- 外部へ書き込む操作は、再試行で変わらない識別子か、外部の正本から照合できるキーを定める。反映の受付と、読み戻して確認した結果を区別する。回答待ちは[質問台帳](#人間の回答を待つ質問の台帳)の記録と関連付ける。

## 人間の回答を待つ質問の台帳

依頼と許可の範囲で、設計、実装、検証、反映の各工程を自律で完了させる。自律実行の仕組みを設計するときも、以下の手順を入出力と状態遷移に組み込む。

1. 自律実行の着手時に質問台帳の正本を必ず開く。未作成なら、許可された永続的な保存先に質問0件で作る。[作業台帳](../../AGENTS.md#作業台帳)が質問の状態を管理できる場合は、同じ正本を使う。
2. 既存の指示、記録、許可、実データを確認し、許可された代替手段と可逆な既定値を検討する。それでも本人だけが持つ情報、権限者の判断、必須の許諾がなければ合格条件を満たせない場合に限り、質問を登録する。対象と判断内容の組で照合し、一つの判断につき一件を登録・更新する。質問ID、質問、回答者、回答が必要な根拠、確認した代替手段、止まる工程、再開条件、状態を記す。機密を含む項目は認可済みの非公開の場所で扱う。
3. 台帳に蓄積した未回答の質問は、依存しない工程を進めたうえで、必要なものをまとめて提示する。回答を待つのはその回答に依存する工程に限る。利用できる情報と道具で進められる残りの工程は、確認を挟まず自律で完了させる。
4. 次の実行で台帳を読み、未回答の質問と現在の再開条件を照合する。有効な回答を得たら回答の参照先を記して回答済みにし、該当工程を再開して検証する。条件が変わって回答が不要になったら、その根拠を記して解消する。回答が必要な工程は状態を記録し、独立した工程を進める。

## 完了条件

設計結果に正本と利用側の参照先を示す。設計のみの依頼で既存定義が競合している場合は、切り替え手順も示す。

自律実行の仕組みでは、回答なしで進む案件と回答が必須の案件を一件ずつ使う。どちらも着手時に台帳を開けることを確かめる。前者では今回の作業に質問が0件であることを台帳から確かめ、作業を完了する。後者では再実行しても同じ質問が一件にまとまり、回答と独立した工程が完了し、回答を記録すれば残りを再開できることを確かめる。

実装や移行を含む依頼では、対象ごとに現行の正本が1件、同じ役割を持つ独立した現行定義が0件であり、普段の読み取り、書き込み、検証が正本につながることを確認する。移行した場合は、前後の識別子、件数、必要な履歴を実レコードで突き合わせる。競合や未確認は残る箇所を記録し、解消できる範囲で統合を進める。

実データで検証できる場合は、[`kafstyler:benchmark`](../benchmark/SKILL.md) を呼ぶ。データの場所、設計した契約、正本と競合定義の件数、利用側の入口、一意性、参照整合性、期待件数を渡す。結果を設計に反映し、確認した契約と検証結果を示す。
