# 反証レビュー

任意の出力で人が読む文章には[imozの執筆・推敲ルール](../../BIBLES.md#imozの日本語編集)を適用する。[出力の共通基準](../../MISSION.md#出力の共通基準)

単独で使うときは利用者の依頼から、別スキルから呼ばれたときは渡された対象・前提・合格条件から、反証する主張を定める。[共通の連携手順](../../AGENTS.md#コマンドの連携)

1. 最初に論文調査、文献調査、Web検索をすべて行う。関連論文の原著、書籍・規格・技術報告、開発元の最新版と実装を調べる。出典の一次URL、版、比較に使える条件を記録し、見つからなかった資料も明記する。
2. 反証する対象に現行の方式がある場合は、置き換える前提で、根拠のある外部手法や既存実装を探す。期待する結果と成立に必要な前提を定める。候補が見つかったら、同じ条件で現行と比較する。前提が崩れたときに最も影響が大きい箇所から調べる。
3. 実物、実際の入力、一次資料を使い、利用者が普段使う経路を最初から最後まで追う。結果が変わる箇所では依存関係、権限とデータの境界、途中失敗、再試行、復旧を確認する。KAFKA2306のWeb UIでは、[かふかのデザインパターン](../../BIBLES.md#かふかのデザインパターン)から設計と検証の基準を開き、空、エラー、未確認の表示やキーボード操作で、利用者の判断や次の操作が止まる例を探す。
   - [差分に応じた検証](../../BIBLES.md#claude-codeの検証)では、レビューするコミットと比較元を固定する。担当者が管理するレビュー規則や合格条件は変更前の正本から読む。差分から該当する過去障害を選び、発動条件、確認方法、元の障害記録を参照する。再レビューでは前回の観測と未解決の指摘を引き継ぎ、変更が影響する箇所を見直す。
4. 同じ証拠から最も有力な対立仮説を立てる。現実に起こり得る反例か境界事例を示し、どの観測で仮説を見分けられるかを定める。反例や再発を実行して測れる場合は、[`kafstyler:benchmark`](../benchmark/SKILL.md) に判別用の入力、手順、期待する観測、依頼の範囲を渡し、測定結果を指摘の根拠に使う。`benchmark` が実行中なら、反例と判別条件を呼び出し元へ返し、そこで測れるようにする。
5. 致命的な指摘から挙げる。中核の結果が成り立たない、普段の利用経路で動作しないか安全に使えない、復旧できない重大な損失が生じる場合を含む。指摘ごとに発生条件、実際の根拠か正確な再現手順、影響、最小の修正か結論を決める確認を記す。実測していないリスクは未確認とする。変更前の同じ操作でも再現した指摘には、既存の不具合であることを記す。
6. 置き換え、修正、停止の判断と、その根拠を示す。合格条件を満たす候補が確認できた場合は、置き換える対象と移行後の確認を示す。根拠のある致命的な指摘が0件なら、重要な確認と影響の最も大きい未確認事項を示す。

呼び出し元には、重大な指摘、判断の根拠、未確認の条件を返す。修正や採否は、元のスキルが依頼の範囲内で扱う。

## 成果物の理由を確かめる

[成果物の確認手順](../../AGENTS.md#成果物の各要素を根拠と照合する)から、対象の版、理由文、原典・要件の該当箇所、yomiyasuの推敲結果を受け取る。各要素を理由に結びつけ、必要な論点に imozuru の調査記録か確認済みの原典・要件があるかを確かめる。

理由文が挙げる根拠を開き、その条件で主張が成立するか、要素を外すと利用者のどの判断や行動に差が出るかを確認する。文章が読みやすくても、根拠が理由を支えない、用途が重複する、成立条件が抜けている箇所は、対象と反例を示して返す。欠けた結果や根拠はレビュー結果に明記し、他の作業を止めない。
