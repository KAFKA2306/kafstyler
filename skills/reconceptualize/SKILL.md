# 概念再構築

依頼を実装可能な仕様へ言い換えるだけで終わらない。依頼やIssueがなくても、実績・失敗・利用状況から放置された問題を自ら発見する。前提や目標そのものを問い直し、現状維持や廃止も含めて完成像を選ぶ。`reconceptualize` は**何に取り組むべきか**を判断し、`autocatalyze` が起動・実行・検証と次の観測を担う。

[自律的に再構築する](#自律的に問題を発見して再構築する) · [合格条件を決める](#合格条件を決める) · [継続運用の条件](#継続運用の合格条件) · [結果から再検討する](#成果物の確認と手順の改善)

## 自律的に問題を発見して再構築する

依頼の有無ではなく、**実際の結果と期待する成果の差**を起点にする。既存の `autocatalyze` の定時・イベント・再開時の観測で、未依頼の問題も探索する。新しい常駐ジョブ、監視台帳、全件巡回は作らない。

1. **自発的に発見する。** 実行履歴、利用の失敗・途中離脱、再発、問い合わせ、Issue、公開結果、維持費や使われない機能を照合する。最初の発見を結論にせず、関連する履歴や別の利用経路を再確認して、未発見の根本原因と重複候補を探す。観測事実・原因仮説・未確認を分離する。問題が見つからないときは修正を作らない。
2. **前提を疑う。** 「このIssueがなくても利用者は困るか」「要求どおり完成しても、何が解決しないか」「機能や目標をなくした方が成果に近づくか」を調べる。既存の機能、目標、評価指標、作業そのものが必要かを問い直す。原因仮説を否定できる観測を決める。
3. **自分で選ぶ。** 問題の候補を利用者への影響、広がり、進展の見込み、確かめる費用で比べる。優先問題に対して現状維持・廃止・再利用・統合・改善・根本的な再設計から、現行延長と別の枠組みの完成像を比較する。採用案と最有力の不採用案を、期待効果、根拠、失敗時の影響で説明する。成果を改善しないIssueの消化や変更件数は評価しない。
4. **小さく確かめる。** 採用案の完成状態、利用者の最後の操作、変更前の実測、合格条件、反証条件を決める。不確実な仮説は最小の観測または可逆的な試行で確かめる。独立した比較は `adjudicate`、重大な反例は `disprove` を使い、採用・現状維持・中止を決める。
5. **実行につなげる。** `autocatalyze` に発見の証拠、優先理由、採用する完成像、退けた案、対象と評価の版、合格条件、最初の実行、停止・再検討条件を渡す。許可済みの範囲では確認待ちにせず実装・検証を進める。正本は `canonicalize` と共有し、別の起動元や重複案件を作らない。
6. **結果から再構築する。** 成果物が合格しても実利用の結果が改善しない、対症療法が再発する、前提を否定する証拠が出る場合は、実装を繰り返す前に手順1〜3へ戻る。成果が改善した場合はその根拠を引き継ぎ、現状維持が最善なら作業を増やさない。

[自律的な問題発見と概念再構築](../../BIBLES.md#自律的な問題発見と概念再構築)を根拠にする。利用者の目的や権限を勝手に広げず、観測に支えられた案件だけを選ぶ。

文書・Obsidian Vaultの改善では、ノート数やプラグイン導入数よりも、必要な答えが見つからない、旧版に誘導される、分類で実在の対象が失われるといった利用上の問題を優先して発見する。[文書管理の根拠](../../BIBLES.md#文書の分類検索鮮度を判断する)を使い、標準検索・既存の目次・別名の修正、統合・退役を、新しいプラグインや分類項目の追加と比較する。

## 合格条件を決める

**まず問題を確かめる。** [Double Diamond](../../BIBLES.md#問題の再定義と利用者の目的)を参考に、再利用・変更・統合・削除・変更しない案を比べる。採用案と最有力の不採用案について理由を残す。「実装した」「Issueを書いた」は合格条件にしない。

1. **最後の操作を決める。** 利用者が普段使う画面・ファイル・コマンド・機器から、最後に何をして何が見えれば完了かを一文で書く。画面なら最初に読む表示、押す場所、成功を示す表示まで決める。KAFKA2306のWeb UIは[操作パターンの正本](../../BIBLES.md#かふかのデザインパターン)に沿って順番を確かめる。
2. **現行の障害を確認する。** 同じ入口から現行の成果物と利用結果を確認する。表面上の障害よりも結果を左右する上流の原因があれば、そちらを優先する。
3. **観測と検証の方法を決める。** 成功と判断できる観測を明確にし、実行と検証に使う既存の道具を選ぶ。時間や費用を要する作業では、上限と停止条件も決める。
   - [実物を使う検証](../../BIBLES.md#claude-codeの検証)に備え、入口、代表入力、最後の操作、そこで観測する結果を先に記録する。完了していないのに途中の表示や終了コードだけで合格する例があれば、最後の結果で判定できる条件に直す。
4. **改善を比較する指標を決める。** 品質を上げる依頼では、現行や初稿を比較基準にする。読者の理解、操作の成功、精度、所要時間など、利用者の結果を左右する指標を一つ以上選ぶ。合格条件と改善を比べる指標を作業前に定める。

技術白書なら、読者が「どの技術を、どの条件で採用するか」を根拠付きで判断できる状態を完成条件にする。対象、比較候補、採否を分ける指標を [didactizationの白書手順](../didactization/SKILL.md#技術白書を構成する) に渡す。

継続して成果を届ける案件では、[継続運用の合格条件](#継続運用の合格条件)も決める。

重要な判断では、利用者が用事を済ませられなくても合格する反例を探す。必要なら [disprove](../disprove/SKILL.md) を使う。比較が必要なら [adjudicate](../adjudicate/SKILL.md) で判定条件を固定する。軽微な変更は既存の確認方法で判断する。

完成場面、合格条件、道具、固定した評価の参照先を示す。

### 継続運用の合格条件

常駐・定期・イベント実行で調査、制作、更新、監視などを続ける場合は、次の二つを決め、[定期実行と再開の評価](../adjudicate/SKILL.md#定期実行と再開の評価)に渡す。

- **一周期の成果。** 入力が変わったときに、誰がどこで、いつまでに、何を確かめられればよいかを決める。取得に成功して変更がない場合、失敗した場合、回答が必要な場合も、それぞれ残す状態と必要な通知を決める。
- **運用全体。** 通常起動が続くこと、同じ入力の再送や中断・再開で確認済みの工程を重ねないこと、実行上限や停止条件を守ることを、観測できる条件にする。通知やLLM呼び出しがある場合は、必要な回数と重複を判定する条件を決める。起動が遅れたときや必要な成果が届かなかったときに、何を観測して対応するかも定める。

既存のIssueまたは実行履歴に、起動を識別するイベントIDまたは予定時刻、実行ID、入力と評価の版、最後の確認と次の起動条件を残す。後続の実行担当には台帳の参照先と合格条件を渡す。[定期実行と再開の記録](../canonicalize/SKILL.md#定期実行と再開の記録)

再起動時は記録を読み戻し、合格条件と確認済みの結果を引き継ぐ。利用者の用事、入口、権限、期限、成果の実測など、合格の判断に効く条件が変わったときは、目的の前提も含めて再検討する。入力の版だけが変わった場合は、固定した条件で次の一周期を判定する。

## 成果物の確認と手順の改善

1. **成果物と問題設定を評価する。** 成果物は利用者の入口で確かめる。品質比較があれば [adjudicate](../adjudicate/SKILL.md) を、文章編集が必要なら [didactization](../didactization/SKILL.md) を使う。変更した箇所に関係する確認を再実行する。合格したのに本来の成果が出ない、または修正を繰り返しても改善しないなら、実装の再試行だけで済ませず、[問題の発見と再構築](#自律的に問題を発見して再構築する)から再検討する。改善案は同じ条件で採否を決める。
2. **不合格の原因を直す。** 不合格の原因が成果物にあれば成果物で直す。Kafstylerの手順や起動に再現できる漏れがあれば、使用した版、再現入力、期待と実際の差を記録する。[更新手順](../../MISSION.md)に従い、利用者が認可した範囲で正本の既存手順を最小限修正し、元の事例と別分野の事例で評価する。
3. **正本へ反映する。** 正本へ反映できる場合は通常の反映経路を使い、反映版を読み戻す。反映できない場合は許可された非公開の記録先か利用者への報告に再現手順と修正案を残す。元の依頼で進められる作業は続ける。
