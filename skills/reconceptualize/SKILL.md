# 概念再構築

依頼を仕様へ言い換えるだけで終わらない。期待と実際の成果の差から未依頼の問題も発見し、何に取り組むかを決める。実行は [autocatalyze](../autocatalyze/SKILL.md) に渡す。

1. MISSION、現行目的、Issue、利用結果、失敗・離脱・問い合わせ、維持費から問題を探す。観測事実、原因仮説、未確認を分け、症状と根本原因を区別する。問題がなければ変更しない。
2. 要求どおり作っても何が解決しないか、その機能・目標・作業自体が必要かを問う。前提を否定する事実と別の問題設定を探す。
3. 利用者への影響、広がり、進展可能性、費用で問題を選ぶ。現状維持、廃止、再利用、統合、改善、根本的再設計を比較し、採用案と最有力代替案の理由を示す。Issue消化や変更件数を目的にしない。
4. 利用者が最後に行う操作と得られる成果を具体化する。入口、対象、必要な情報、期限、費用、権限、停止条件を決める。画面なら最初に見る情報、操作、結果を設計する。
5. 弱い前提は [disprove](../disprove/SKILL.md)、選択肢の比較は [adjudicate](../adjudicate/SKILL.md) を使う。採用した問題・完成像・根拠・最初の実行・停止条件を渡す。正本は [canonicalize](../canonicalize/SKILL.md) と共有する。使命変更は権限者に委ねる。
6. 実際の利用結果が前提を否定したら、実装を繰り返す前に問題設定へ戻る。

## 継続運用・知識・白書

- 定期・イベント実行では一周期の成果、期限、次の起動、差分なし・取得失敗・判断待ちの扱いを定める。通常保守と毎回成果を生む調査・制作を区別し、既存起動元を使う。
- 知識では利用者の問いから正本への到達を考え、同名別対象、旧版誤誘導、重複、欠落を問題候補にする。名称・別名・目次・統合・退役と新機能を比較する。
- 技術白書では読者が何を採否判断するか、対象・候補・根拠・条件を [didactization](../didactization/SKILL.md) へ渡す。
