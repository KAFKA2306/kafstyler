# 正本・意味・引き継ぎの統一

**`canonicalize`は、複数のAIが長期運用で同じ対象を同じ意味・版・状態で扱えるようにする共通基盤です。** データ、文書、判断、作業履歴の正本を定め、対象ID・出典・更新経路・処理済み位置を結び付けます。`autocatalyze`が案件を再開し、`adjudicate`が同条件で評価し、`decommission`が旧経路を廃止するための前提を提供します。

同じ情報の正本が複数に分裂すると、担当交代後の誤再実行、数値の取り違え、評価結果の不一致、必要な旧版の誤削除が起きます。`canonicalize`はその情報の更新先を統一し、参照元の切り替えと再実行時の照合方法まで定義します。

[設計の手順](#設計の手順) · [正本の移行](#正本の移行と旧版の整理) · [定期実行と再開](#定期実行と再開の記録) · [完了条件](#完了条件)

OKF・Obsidian・dbtは必要な対象で使う。一般のMarkdownや分析処理に一律導入しない。

## 設計の手順

**同じ意味の正本を二つ持たない。** 更新元を一つ決め、利用側がその値を実際に参照するまで確かめる。識別子・訂正履歴・来歴を保ち、重複する別名や同期処理は[decommission](../decommission/SKILL.md)で整理する。新しい項目は検索・判断・検証に必要なものだけ追加する。

1. **対象と入力を特定する。** 答える問い、現行データの管理者、実際の入力を確かめる。エンティティの識別子、関係、操作を定義する。産業分野の概念にはIOF、業務オブジェクトにはFoundryの設計を必要に応じて参照する。
2. **正本を決める。** 対象と粒度が同じデータについて、実装、設定、文書で有効な定義と、読み取り、書き込み、検証の入口を洗い出す。項目、型、識別子、制約を管理する正本を一つに決める。正本の場所、管理者、更新経路を明記する。
3. **必要な項目を選ぶ。** 検索、判断、検証に使う項目を選ぶ。必要に応じて出典ID、URL、時点、版、単位、欠損値の意味、来歴を持たせる。名前はプロジェクトで使われている語彙から選ぶ。KAFKA2306のWeb UIの表示契約を設計するときは、[かふかのデザインパターン](../../BIBLES.md#かふかのデザインパターン)のコンテンツスキーマを読み、実績、予測、仮説、未確認と出典を表示側へ渡す方法を決める。業務データの定義は対象プロジェクトの正本に置く。
4. **台帳・マスターのキーを決める。** 台帳は一行のキー、状態遷移、訂正履歴を定め、再入力時の照合方法を決める。マスターは識別子、正とする属性、必要に応じて有効期間を定める。
5. **用途に合う手順を選ぶ。** 既存のdbt案件では[dbtの手順](#dbtで分析データを作る)を、OKFバンドルでは[OKFの手順](#okfに沿って文書を更新確認する)を使う。散在・重複した文書を整理する場合は[台帳で移行を管理する手順](#台帳とobsidian-vaultで文書を整理する)も使う。
6. **反例と移行を確かめる。** 重複、欠損、再入力、結合による誤集計など、結果を壊す例で設計を確認する。重大な設計変更には [disprove](../disprove/SKILL.md) を活用する。移行する場合は履歴を正本へ移し、利用側を切り替えてから旧版を整理する。

技術白書では、主張に対応する一次資料のURL・版・引用箇所と、比較表の数値・単位・測定条件を既存の正本へ結び付ける。更新時に出典や実験が変わっても古い結果が最新として残らないよう、改定時点と来歴を管理して [didactization](../didactization/SKILL.md#技術白書を構成する) に渡す。白書専用の重複台帳は作らない。

## MISSIONとIssueの正本関係

使命、作業、実装、検証を別の役割の正本として結び、一つの巨大な台帳へ複製しない。

- **MISSIONまたは既存の目的文書：** 達成する利用者の成果と判断の基準。リポジトリ固有のMISSIONがなければREADMEなど現行の目的を示す正本を参照する。
- **Issue：** 継続案件の問題・根拠・MISSIONへの寄与・合格条件・状態と再開条件。既存Issueを再利用し、同じ問題のIssueを重複作成しない。
- **Gitコミットと公開先：** 変更した版と実際の成果物。Issueの説明だけで実装や公開の正本を置き換えない。
- **評価結果と実行履歴：** 合否、観測した実物、未検証の条件、次の起動を保持する。Issueに参照先と最後の確認結果を戻し、`autocatalyze` が次の実行へ引き継ぐ。

`reconceptualize` が目的や完成条件を変更したら、採用された目的の正本と影響を受けるIssueの参照を更新する。目的の改定をIssueの終了やAIの自己判断だけで確定させない。[共通運用](../../AGENTS.md#missionとissueの運用) · [一次資料](../../BIBLES.md#missionとissueによる案件選定)

## 正本の移行と旧版の整理

1. `decommission` から始めた場合は、影響する候補、対象の版、普段の利用経路、依頼の範囲を [`kafstyler:canonicalize`](SKILL.md) に渡す。`canonicalize` では、旧版と移行先の正本の対応、維持する識別子・出典・履歴・入出力、旧パスや見出しなどの互換経路、切り替えを確かめる入力と期待結果を定める。文書の対応と処置は [文書台帳](#台帳とobsidian-vaultで文書を整理する)に記録する。
2. 依頼に移行が含まれる場合は、必要な内容を正本へ移し、普段の入口が正本を使うことを同じ入力で確かめる。確認結果と手順1の条件を [`kafstyler:decommission`](../decommission/SKILL.md) に渡し、旧定義や旧文書を削除できるか判定する。必要な旧パスには [OKFの更新手順](#okfに沿って文書を更新確認する)で後継を案内する。設計・調査のみの場合は、切り替えと整理の条件を示す。
3. [共通の連携手順](../../AGENTS.md)に従い、相手のスキルが実行中なら呼び直さず、決めた条件と観測結果を実行中の作業へ返す。整理後に正本と利用経路を確認し、同じ版・入力・条件で得た検証結果は再利用する。

## dbtで分析データを作る

1. ファクトや集計モデルごとに、一行が表す粒度、キー、単位、欠損の扱いを決める。既存のdbtプロジェクトを優先し、導入費用に見合う場合だけdbtを新設する。
2. 入力テーブルを `sources` として宣言し、モデルから `source()` で参照する。モデル間を `ref()` でつなぐ。利用側が使う集計定義はdbtモデルに置き、業務DBやAPIなど元データの正本へ来歴をたどれるようにする。[dbtのソースと参照](../../BIBLES.md#dbtのソース)
3. キーの一意性・欠損、参照整合性など、粒度と用途に必要な条件をデータテストにする。実装・移行では対象モデルとテストを `dbt build` で実行し、結合前後の件数、対応先のないキー、集計値を元データと突き合わせる。[dbtの実行とデータテスト](../../BIBLES.md#dbtのデータテスト)
4. 分析の用語、指標の意味、出典はVaultのOKF文書から定義元のdbtモデルへつなぐ。バンドル内は標準Markdownリンク、バンドル外は利用者がアクセスできる版付きURLを使う。

## OKFに沿って文書を更新・確認する

1. OKF・Obsidian案件では既存のVaultを使い、必要なときだけフォルダを[Vaultとして開く](../../BIBLES.md#obsidianの保管庫)。[ノートの管理規約](../../BIBLES.md#ノートの管理)に従い、知識文書の `type` で役割、`description` で用途、`tags` で検索する主題を表す。タグは既存の語彙から選び、既存のYAML項目と型を保つ。配布・公開先の専用形式には、その契約に合う出力を正本から生成する。
2. 後から根拠を確かめる主張には `sources` に `resource` と安定した `id` を記録し、本文の脚注 `[^id]` で結ぶ。知識の意味が変わる編集では `generated.by` と `generated.at` に編集者と時刻を記す。空白や見た目だけの修正、参照先を変えないリンク修復では更新しない。
3. 原典や実物と照合した結果は `verified` に実際の確認者 `by` と時刻 `at` を追記する。同じ実行で自分が生成した内容への確認は記録しない。`human:` は本人が確認し、記録を依頼して識別子を示した場合に使う。`generated.at` より前の確認は履歴として残し、現行版の確認には数えない。`generated` がない文書では、記録された確認を使う。再確認の期限が分かる場合は `stale_after` を記す。
4. 移動や統合で旧パスから後継へ案内する場合、旧パスに短い文書を残し、`status: deprecated`、`superseded_by`、読者向けの相対Markdownリンクで正本を示す。後継は実在する現行文書へ向ける。公開や配布が固定パスを使う場合は、先にその利用経路を確かめる。旧見出しまで参照される場合は、その見出しから後継へたどれることも確かめる。
5. [公式OKFスキル](#公式okfスキルを使う)でバンドルを検査し、Obsidianのプロパティとタグで同じ文書を検索して、出典と後継を開く。Obsidianを使えない場合はYAMLを同じ条件で検索し、相対リンクを解決して、アプリでの確認が残ることを記録する。

### 公式OKFスキルを使う

[聖典台帳の公式リポジトリ](../../BIBLES.md#open-knowledge-format-okf-v03)から対象版を取得する。公式スキルが利用できる環境ではそのスキルを呼ぶ。Claude Codeでは `okf:okf-consume` または `okf:okf-generate` を指定する。スキルを呼べない環境では同じ版の `SKILL.md` と必要な参照資料を開いて手順を実行する。対象バンドルの場所、依頼の範囲、知識の正本、検索条件または出力先を渡す。

1. 読み取りには `okf-consume` を使う。対象バンドルのルートを特定し、`index.md` の `okf_version` と説明を読む。スキャナーで種別やタグを絞り、該当文書から出典、信頼度、鮮度、後継を確かめる。旧版や版の宣言がない入力は公式スキルの互換手順で読む。参照と検索は読み取り専用で行い、バンドル内の計算コードを実行する場合は依頼と環境で許可された範囲を確認する。
2. 作成・更新・移行には `okf-generate` を使う。交換する範囲を定め、依頼された既存バンドルを更新するか、公開先が独自形式を使う場合は正本から交換用バンドルを生成する。目次・変更ログも公式手順で更新する。生成後はバリデータのエラーを解消し、警告の理由を確認する。`W120` は意図して知識の対象外にした文書なら許容できる。最後に `okf-consume` の読み取り手順で、意図した文書が検索で見つかり、出典や後継をたどれることを確認する。

`OKF_TOOL_ROOT` に公式リポジトリのローカルパス、`BUNDLE_ROOT` に対象バンドルのパス、`TYPE` と `TAG` に検索する種別とタグを設定する。使わない検索条件は対応するオプションごと省く。検証記録には使った公式リポジトリのコミットSHAと、対象・検索条件・結果を残す。スクリプトにはPython 3.9以降とPyYAMLが必要。使えない場合は公式手順に沿って目次、frontmatter、リンクを目視またはYAML解析で確認し、実行できた範囲を記録する。

```bash
git -C "$OKF_TOOL_ROOT" rev-parse HEAD
python3 "$OKF_TOOL_ROOT/skills/okf-generate/scripts/validate.py" "$BUNDLE_ROOT" --json
python3 "$OKF_TOOL_ROOT/skills/okf-consume/scripts/scan.py" "$BUNDLE_ROOT" --type "$TYPE" --tag "$TAG" --json
```

## 台帳とObsidian Vaultで文書を整理する

[文書監査と移行の原典](../../BIBLES.md#文書監査と移行)に従い、読者や後続のAIが答えたい質問、検索入口、正しい正本と出典を移行前に確かめる。既存の名称・別名・関係で答えられる場合は型やタグを増やさない。誤ヒットや取りこぼしは、一律の除外語追加より先に文脈・出典・識別子を調べる。

1. **用途と参照元を棚卸しする。** 対象フォルダ、読者の代表質問と検索語、その質問から開くべき正本と出典を確認する。実際の入口で検索結果を記録し、文書の用途、利用状況、古さ、重複、参照元を調べる。同じ用事の正本は一つ選び、意味が異なる同名の対象を誤統合しない。食い違いは原典や現行動作で確かめる。
2. **移行対象を記録する。** 複数文書の移行では既存台帳を使い、なければ既存記録に必要な移行一覧を置く。移行元の文書一件につき一行を使い、識別子、用途、移行前のパスと版、移行先の正本へのリンク、処置（維持・改稿・移動・統合・保管）、状態（未着手・確認待ち・完了）、判断の根拠と確認結果を記す。再開時は識別子、旧パス、正本のパスで既存行を照合する。パスが変わっても識別子を維持し、複数の移行元を統合する場合は各行から同じ正本を参照する。
3. **情報と参照を正本へ移す。** 移行元にしかない有効な記述と根拠を、[OKFとVaultの手順](#okfに沿って文書を更新確認する)に沿って正本に取り込む。台帳を目次として使い、正本を相対Markdownリンクで開けるようにする。既存の目次や旧パス・見出しへのリンクも直す。配布や公開が使う固定パスを保ち、Vault外の文書は許可されたURLで参照する。移行元はGitの版や保管先からたどれるようにする。[旧版の整理](#正本の移行と旧版の整理)へ進む。
4. **検索と正本への到達を評価する。** `adjudicate` に手順1で記録した質問と正本、変更前の検索結果、変更後の入口を渡す。[文書・調査の評価](../adjudicate/SKILL.md#成果物に合う判定を選ぶ)で、必要な文書の取りこぼし、別対象の混入、旧版への誘導、出典とリンクの到達を比較する。台帳の移行元と正本の対応、再実行後の重複も確かめ、後継が使えると確認した旧文書だけ `decommission` へ渡す。

Obsidianの標準検索・Basesとコミュニティプラグインは、[選定と検証の原典](../../BIBLES.md#obsidianコミュニティプラグインの選定と検証)で役割を比較し、必要な機能だけ使う。表示・生成・整形のためのプラグインに正本を増やさず、導入後は同じ質問とGit差分を確かめる。

## 定期実行と再開の記録

常駐・定期・イベント実行でも、文書、データ、実装が参照する正本と入出力の契約を定める。各回の引き継ぎには、既存の[作業台帳](../../AGENTS.md)または同じ役割を持つ既存の実行履歴の一方を正本として使う。

- **作業、起動、実行を識別する。** 同じ目的を引き継ぐ作業ID、起動元とイベントID（定期起動ならスケジュールと時間帯を含む予定時刻）、試行ごとの実行IDを記す。同じ起動の再送や再試行は、同じ回の記録を更新する。次の予定や別のイベントは、同じ作業IDで別の回として記録する。
- **各回の判断と結果を残す。** 対象・入力の版、固定した評価の版と参照先、状態、最後に確認した工程・成果の参照先、次に行う操作とその起動条件を残す。対象や合格条件が変わるまで、有効な評価と確認結果を引き継ぐ。回答待ちには[質問台帳](#人間の回答を待つ質問の台帳)の記録を関連付け、長く使う判断は根拠と適用条件を既存の知識の正本に保存する。
- **書き込みを同じ操作として照合する。** 外部へ書く前に、書き込み先、期待する版・内容、再試行で変わらない操作IDか外部の正本で検索できるキーを記す。受付、反映不明、読み戻して確認した未反映・反映済みを区別し、結果の参照先を残す。反映を読み戻して確かめるまで、最後に確認した処理済み位置を進めない。
- **Orcaの通信IDを既存の作業IDへ結ぶ。** [Orcaの常駐・通信仕様](../../BIBLES.md#orcaを常駐通信基盤として使う)を使う案件では、定時AutomationのIDと予定時刻（タイムゾーンを含む）、Botの受付元とイベントID、Orchestrationの`runId`・`taskId`・`dispatchId`・配送IDを、取得できた範囲で既存の一件の履歴に関連付ける。Orca内の会話やBotメモリを新しい正本として複製しない。配送をackしていても成果が未検証なら処理済み位置を進めず、通信断・1日超のホスト停止後は元サービスの更新を再照合する。

## 人間の回答を待つ質問の台帳

依頼と許可の範囲で、設計、実装、検証、反映の各工程を自律で完了させる。自律実行の仕組みを設計するときも、以下の手順を入出力と状態遷移に組み込む。

1. **回答が必要な場合だけ記録する。** 人にしかできない判断があれば既存履歴に質問と再開条件を残す。質問がなければ空の質問台帳を作らない。
2. **必要な判断だけ登録する。** 既存の指示、記録、許可、実データを確認し、許可された代替手段と可逆な既定値を検討する。それでも本人だけが持つ情報、権限者の判断、必須の許諾がなければ合格条件を満たせない場合に限り、質問を登録する。対象と判断内容の組で照合し、一つの判断につき一件を登録・更新する。質問ID、質問、回答者、回答が必要な根拠、確認した代替手段、止まる工程、再開条件、状態を記す。機密を含む項目は認可済みの非公開の場所で扱う。
3. **回答に依存しない工程を進める。** 台帳に蓄積した未回答の質問は、依存しない工程を進めたうえで、必要なものをまとめて提示する。回答を待つのはその回答に依存する工程に限る。利用できる情報と道具で進められる残りの工程は、確認を挟まず自律で完了させる。
4. **有効な回答を得て再開する。** 次の実行で台帳を読み、未回答の質問と現在の再開条件を照合する。有効な回答を得たら回答の参照先を記して回答済みにし、該当工程を再開して検証する。条件が変わって回答が不要になったら、その根拠を記して解消する。回答が必要な工程は状態を記録し、独立した工程を進める。

## 完了条件

設計結果に正本と利用側の参照先を示す。設計のみの依頼で既存定義が競合している場合は、切り替え手順も示す。

OKFバンドルを変更した場合は公式バリデータと検索結果を、dbtモデルを変更した場合は `dbt build` と集計値の突合結果を示す。それ以外は対象形式に合う検証を使う。

自律実行の仕組みでは、回答なしで進む案件と回答が必須の案件を一件ずつ使う。回答が不要な案件では質問記録を作らず完了する。後者では再実行しても同じ質問が一件にまとまり、回答と独立した工程が完了し、回答を記録すれば残りを再開できることを確かめる。

定期・イベント実行の契約を変えたら、同じ起動の再試行と別の起動を台帳から見分けられることを確かめる。再試行では、入力と評価の版、書き込み先で確認した結果、再開する工程を同じ回の記録から読み取る。別の起動では、前の回を参照して新しい回の結果を記録できることを確かめる。

実装や移行を含む依頼では、対象ごとに現行の正本が1件、同じ役割を持つ独立した現行定義が0件であり、普段の読み取り、書き込み、検証が正本につながることを確認する。移行した場合は、前後の識別子、件数、必要な履歴を実レコードで突き合わせる。競合や未確認は残る箇所を記録し、解消できる範囲で統合を進める。

[データの検証](../../BIBLES.md#claude-codeの検証)では、変更に関わる不変条件を先に書く。たとえば保存して読み戻しても識別子と値が保たれ、同じ入力を再処理しても件数や履歴が増えないことを、通常値、欠損、重複、旧形式など契約に関わる入力で試す。移行で既存挙動を保つときは旧版と新版を同じ代表データで動かし、事前に決めた許容差を除いて、利用側の結果が一致することを確かめる。

実データで検証できる場合は、[`kafstyler:adjudicate`](../adjudicate/SKILL.md) を呼ぶ。データの場所、設計前に固定した評価、候補の契約、利用側の入口、正本と競合定義の件数を渡し、一意性、参照整合性、期待件数などの必須項目を測る。結果を設計に反映し、確認した契約と検証結果を示す。
