# AIスロップ削除

不要なものを減らしながら、仕様・実装・設定・文書が互いに矛盾せず、利用者が普段の入口から必要な操作を続けられる状態を保つ。

任意の出力で人が読む文章には[imozの執筆・推敲ルール](../../BIBLES.md#imozの日本語編集)を適用する。[出力の共通基準](../../MISSION.md#出力の共通基準)

着手前に、かふかのZenn記事を3本読み、対象に当てはまる整理基準を選ぶ。

- [なぜAIに任せるほど、あなたのコードは複雑になるのか](https://zenn.dev/kafka2306/articles/2026-08-16-ai-added-decision-cost-audit) 重複する指示・検証・状態・分岐を洗い出し、削除後も機能・正しさ・必要な証拠が揃うかを確かめる。 [聖典台帳](../../BIBLES.md#aiが増やす判断箇所)
- [AIに同じ指示を繰り返すのをやめた。Issue駆動開発という最小運用](https://zenn.dev/kafka2306/articles/issue-driven-development) 終わった変更の経緯をIssueに残し、現在の仕様として必要な記述を正本に集約する。 [聖典台帳](../../BIBLES.md#issue駆動開発)
- [AIを「過保護」にするな。スタックトレースを聖典とする開発規律 "Crash-Driven Development"](https://zenn.dev/kafka2306/articles/11cd731eebded1) 障害の原因を隠す広すぎる例外捕捉やフォールバックを見直し、根本原因を観測できる形にする。 [聖典台帳](../../BIBLES.md#失敗原因が見える実装)

1. 利用者が普段使う入口と、残すべき仕様・データの正本を特定する。削除候補の参照元と実際の呼び出し元を確認し、残す挙動や入出力を整理前に確かめ、比較が必要なら入力と観測結果を記録する。
2. 同じ役割のフォルダを既存の管理先に統合する。未使用ファイル、空のフォルダ、重複したMarkdown、実行されないコード、処理を素通しするだけのPython・TypeScriptのラッパーを削除する。一つのプログラムに一つの仕事を持たせ、必要に応じて標準入出力でつなぐ。既存の[評価結果](../benchmark/SKILL.md)があれば、置換済みの手順を割り出すために使う。
3. 結論の繰り返し、意味の薄いバッジ、未使用のプレースホルダー、不要な作業説明、場当たり的な名称を削る。削除する箇所にしかない事実、指示、適用条件は、削除前に正本へ移す。
4. 移動・削除と同じ変更で、インポート、リンク、設定、呼び出し元を更新する。整理後の実装・設定・文書を正本に照合し、普段の利用経路で必要な挙動と入出力を確かめる。削除前後の比較が必要で、同じ確認の結果がまだなければ、Claude Codeの `Skill` ツールで [`kafstyler:benchmark`](../benchmark/SKILL.md) を呼ぶ。対象の入口、削除前の入力と観測結果、合格条件、変更範囲を `args` に渡す。変更で生じた食い違いや参照切れを解消し、整理した箇所と確認結果を示す。
