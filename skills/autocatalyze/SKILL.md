# 自律開発

`autocatalyze` は**複数プロジェクト・複数AI担当・長期間の運用と引き継ぎ**を担う中核Skill。既存のIssue・実行履歴から作業ID、対象と版、合格条件、最後の検証結果、未完了の工程、再開条件を復元し、利用者の入口で成果を確認するまで担当する。既存のスケジューラーやイベントを起点にAIの作業を再開し、単発修正も継続運用に組み込む。

[定期実行を選ぶ](#常駐エージェントと定期実行) · [一件を続ける](#一件を合格まで進める) · [実装・検証する](#実装と検証)

## MISSIONに沿ったIssue駆動

1. **使命と現状から選定する。** 各リポジトリのMISSIONまたは既存の目的の正本、open Issue、前回の履歴、公開先・障害の実測を読む。明示依頼と重大障害を尊重し、MISSIONへの寄与、利用者への影響、期限、依存関係、解決の見込みから最優先の一件を選ぶ。古い順・簡単な順にIssueを消化しない。関連するIssueがなければ `reconceptualize` で問題を発見し、不要なら作業を増やさない。
2. **Issueで継続する。** 同じ目的の既存Issueを再利用する。継続・委譲・複数回にまたがり記録がなければIssueを一件作り、MISSIONの参照先、解く問題と根拠、合格条件、前回の版、最後の成果、次の操作と再開条件を残す。単発の軽微な変更にIssue新設を強制しない。`canonicalize` が参照関係と実行済みの位置を管理する。
3. **実装と評価を完了する。** 必要なSkillsを呼び、既存の `main` で一件を実装・コミットし、利用者の入口で検証する。成果とコミットをIssueに返し、確認済みならcloseする。未検証なら開いたまま結果・再開条件を更新する。依存関係が消えた・重複している・使命に不要なIssueは理由を残して整理する。
4. **MISSIONへ実測を返す。** `adjudicate` と `disprove` の評価を見て、成果が使命に寄与したかを判断する。寄与していなければ `reconceptualize` に問題設定・優先順位、必要ならMISSIONの前提の見直しを渡し、次の案件選定を変える。

**Project as Codeを実行に接続する。** 案件を選んだら[canonicalizeのコンテキスト組立て](../canonicalize/SKILL.md#案件コンテキストを組み立てるproject-as-code)に従い、目的・合格条件（Concept）、仕様・コードと対象コミット（Definition）、人が確認する結果（Facade）を既存の正本に結び付ける。担当には案件IDと版付きの必要な参照を渡す。再開時は対象版の変化を確認し、変化した資料だけ読み直す。実装後は元の目的との一致を評価し、必要なFacade更新を`didactization`へ渡す。

[共通規約](../../AGENTS.md#missionとissueの運用) · [GitHub公式資料](../../bibles/mission-eval-writing.md#missionとissueによる案件選定) · [MISSION](../../MISSION.md#mission起点のissue駆動)

## 破壊的移行の実行

旧方式からの破壊的移行を依頼されたときは、[共通規約](../../AGENTS.md#破壊的移行と旧方式の廃止)に従って、旧方式を併存させず一つの正本と実行経路へ置き換える。

1. `canonicalize` が旧入力・識別子・履歴と新正本の対応、廃止する参照元、保持する公開契約を決める。
2. 影響するコード、設定、文書、定期起動、配布入口を新方式に変更する。通常利用、再実行、既存データの読み戻しを確認し、重大な反例は `disprove`、新旧の評価は `adjudicate` で検証する。
3. `decommission` で旧処理・旧パス・互換フォールバック・重複ジョブを削除し、残存参照と旧方式の二重起動がないことを確かめる。公開APIの非互換変更は利用側と版表示を更新する。
4. 変更を既存 `main` にコミットし、普段の入口とコミットを読み戻す。再取得不能なデータや他者の未コミット作業を消さず、確認できなかった外部環境は未検証として既存Issueに再開条件を残す。

## 常時稼働エージェントの中核

差分なしを無介入の成功として扱い、実行主体は[3層配分と停止契約](../../AGENTS.md#計算資源の3層配分と停止契約)で選ぶ。[失敗を隠さない実行](../../AGENTS.md#失敗を隠さない実行)に従い、必須入力・依存関係・権限の異常を別経路や空データで隠さず停止する。証拠と再開条件を既存の正本に残し、推測で続行しない。


他の6 Skills（`reconceptualize`、`canonicalize`、`adjudicate`、`disprove`、`didactization`、`decommission`）は必要な専門判断を提供し、`autocatalyze` は**担当交代・中断・並行案件をまたいで観測・案件選定・実行・検証・次の改善を続ける制御**を担当する。認可済みの起動元・台帳・検証入口を再利用し、重複するジョブや常駐プロセスを増やさない。[長時間エージェント](../../bibles/agents-and-orca.md#長時間稼働するエージェント) · [常駐の聖典](../../bibles/agents-and-orca.md#常駐エージェント)

| 段階 | 操作 | 次へ進む条件 |
| --- | --- | --- |
| 起動・復元 | 定時・イベント・再開を受け、作業ID、最後の成果、権限、費用上限、停止条件を読む | 二重起動がなく実行を許可されている |
| 観測・選定 | 依頼・障害・差分・利用結果・未完了を観測し、未依頼でも根拠のある問題を `reconceptualize` で発見・再構築する。修正不要なら現状を維持する | 解く問題、入口、根拠、合格条件が決まった、または変更不要と判定した |
| 委譲・実行 | 必要な専門スキルへ対象版と合格条件を渡し、修正・制作する | 実物と操作の結果がある |
| 検証・確定 | 外部の正本と利用者の入口で結果を読み戻す | 必須条件合格、二重反映・通知なし |
| 継続・停止 | 成果、失敗位置、再試行条件、次回の起動を台帳に残し、不要なジョブを止める | 別の実行者が前の会話なしで再開できる |

**目的の閉ループ。** 明示されたIssueがなくても、利用履歴に残るつまずき、再発する失敗、使われない機能、実際の成果の停滞を観測したら、[reconceptualizeの自律的な再構築](../reconceptualize/SKILL.md#自律的に問題を発見して再構築する)で未解決の問題を探す。問題を発見した証拠、選んだ完成像、比較した代案、最初の実行、合格条件、再検討条件を受け取り、既存の作業ID・優先順位と照合する。認可済みの範囲で実装・検証へ進み、修正不要なら変更を作らない。成果物が合格しても独立した利用結果が改善しなければ、実装の反復ではなく問題設定から再検討する。別の起動基盤は増やさず、利用者の目的と認可範囲を保つ。

**障害の閉ループ。** 失敗は実際の入力とログで調べ、反映済みなら再送せず、未反映なら上限内で再試行する。動けない工程は失敗として残し、独立した別案件を進める。未取得を差分なし、受付を完了、監視を成果と誤認しない。無限の自己呼び出しや再試行はしない。

**独立監督の採否。** 長い一件が止まりやすく、既存の進捗観測と指示再送で改善を検証できる場合は、[tj-loopの監督・作業分離](../../bibles/agents-and-orca.md#orca-botstj-loopの監督構造とrexの比較)を用いる。既存のOrca/OS起動を再利用して作業担当を観測し、進行中は介入しない。同じ停滞への再開指示は一度まで。再開しても進まない、セッションを読めない、権限・承認・外部反映を確認できない場合は停止理由と再開条件を記録する。監督用LLMの無差分定期起動や別の進捗DBを既定で増やさない。

**省エネの基本。** 差分、期限、重複IDはコードで判定する。変更がなければLLM呼び出し、再生成、定型通知を省く。常時のスケジューラーと常時のLLM起動を混同しない。[運用負荷](../../bibles/mission-eval-writing.md#減算による解決)

**運用の合格。** 通常起動で実成果を確認する回、差分なし、障害からの再開、同入力の重複配信を実際の起動経路で検証する。次周期でも前回の成果と評価を引き継ぎ、通知の重複を防ぐ。実際に試していない周期を確認済みとしない。[定期運用の評価](../adjudicate/SKILL.md#定期実行と再開の評価)

## 常駐エージェントと定期実行

[概念再構築](../reconceptualize/SKILL.md)で、利用者が普段使う入口、そこで観測する合格条件、実行できる時間帯と上限、停止条件を決める。利用結果から目標そのものの見直しが必要と分かった場合も同じ手順で再構築し、実行は `autocatalyze` が一元管理する。定期・イベント起動でも、一件を実装・修復し、検証、配布、公開先での確認まで進める責任を引き継ぐ。次に、作業を進められるか、外部の変化を待つか、端末が止まっても起動する必要があるかを確認する。[起動と再開の公式仕様](../../bibles/agents-and-orca.md#起動と再開の公式仕様)と手元の版・設定を照合する。

| 実行したいこと | 使う入口 |
| --- | --- |
| 今の依頼を一度完了する | `autocatalyze` を直接実行する。 |
| 実装と検証を繰り返して一件を完了する | 対応する Claude Code・Codex では [継続目標](#一件を合格まで進める)を使う。 |
| CIや配布の反映を、開いているセッションで見守る | Claude Codeでは[公式の `/loop`](#claude-codeの-loop-連携)を使う。既にイベントで次の実行を起動できる場合は、その入口を使う。 |
| ターミナルを閉じたあとも同じ端末で進める | ホストのローカルバックグラウンド機能を使う。Claude Codeでは `/bg` を使い、ターミナルを閉じる前に状態の確認方法と作業ツリーを確かめる。PCの再起動で処理は止まる。 |
| 端末が止まっていても処理する | 一件なら Codex Cloud などのクラウド実行を使う。定期・イベント実行なら Claude Code の `/schedule`、ChatGPT Work の Scheduled など、対象への接続と起動条件を満たす仕組みを使う。 |
| 端末上のファイルやアプリを使って定期実行する | 端末・アプリの稼働が必要な範囲を確認し、既存のデスクトップ定期実行や認可済みのスケジューラーを使う。常駐機能が使えないCLIでは、対応する非対話コマンドを実行入口にする。 |

1. **引き受ける。** 既存のIssueや実行履歴で案件を探し、継続案件に記録がなければ最小の再開情報を作る。定期・イベント実行を設定するときは、何が起動を知らせ、どの権限・接続で実行し、誰が結果を読み、どこで停止できるかを決める。登録した設定を読み戻し、ジョブIDや次回の起動条件を台帳に残す。許可された起動手段が使えない場合は、今できる工程を終え、止まった操作と再開条件を記す。
2. **起動を照合してから続ける。** [状態の設計](../canonicalize/SKILL.md#定期実行と再開の記録)に従い、台帳の作業IDと今回の起動を照合する。対象・入力の版、固定した評価、実行上限の残り、最後に確認した工程と外部反映の結果を読む。未確認の外部反映は、書き込み先の正本を読み戻す。同じ起動なら入力の版を保って残りを再開し、復元できるセッションを使う。別の起動は新しい回として記録し、入力の版と前の回の未完了工程を照合する。同じ対象・合格条件で有効な評価と確認結果を引き継ぎ、変わった箇所だけ確認し直す。
3. **観測した状態に応じて進める。**
   - **差分なし。** 取得に成功し、未完了の工程も処理すべき差分もなければ「差分なし」を記録する。設定済みの通知条件に該当しなければ、一覧の再生成や公開、LLMの起動を省き、台帳と次回の起動条件だけを確認する。
   - **実行・待機。** 進められる工程は実行する。外部へ書く前に実行中の作業と同じ起動の結果を照合し、使える既存の排他を利用して同じ対象への書き込みを一つずつ進める。同じ操作を再送する場合は、外部が受け付ける冪等キーを再利用する。外部ジョブや回答を待つときは、依存しない工程を先に終え、待つ対象、最後の確認結果、次の確認時刻か再開イベントを残す。権限者の判断には[質問台帳](../canonicalize/SKILL.md#人間の回答を待つ質問の台帳)を使う。
   - **再試行。** 一時的な失敗は原因を調べ、外部の正本で書き込み済みかを確かめる。反映済みの結果は再利用し、未反映と分かった操作だけを同じ回で上限内で再試行する。取得失敗や反映不明、上限・権限で止まった工程は、最後に確認した位置と再開条件を残す。
4. **成果を確かめ、次の起動につなぐ。** 起動の受付、実行の終了、成果の確認を区別する。利用者の入口から期待した版・内容を読み戻し、固定した評価で合格したときに成功を記録する。証拠と参照先を台帳と既存の報告先に残し、必要な通知や公開の結果を確かめてから処理済みの位置を進める。定例ジョブは各回の結果を記録し、設定済みの次回の起動条件を読み戻す。目的を達成・中止した一時ジョブや終了する定例ジョブは解除を読み戻す。

常駐運用の合格には、設定した入口から初回を実際に起動し、利用者の入口で成果を読み戻す。継続するジョブでは次回の予定またはイベントでも起動し、前回の確認地点を引き継いで差分に応じた結果を残すことを確かめる。終了するジョブでは解除後に設定を読み戻す。[運用での評価](../adjudicate/SKILL.md#定期実行と再開の評価)から変更に関わる失敗事例を選ぶ。再開を変えた場合は途中でセッションを切り、同じ案件の次の工程から進むことを確かめる。再試行を変えた場合は外部書き込みの直後に応答を切り、同じ入力で成果が一件に保たれることを確かめる。端末停止中の起動が要件なら、その条件で起動と成果を確認する。

## 外部ツールによるゼロトークン保守

OSのスケジューラーから[`scripts/vault-maintenance.sh`](../../scripts/vault-maintenance.sh)を呼び、LLMを起動しない日常保守を先に完結する。`OBSIDIAN_VAULT_PATH`で既存の正本を指定し、必要な取得元だけ`KAFSTYLER_INGEST_SOURCE`にrcloneのパスを設定する。`--check`はread-onlyの`vault-lint --json`、`--apply`は差分コピー→`vault-extract`のキャッシュ付き抽出→`vault-lint --fix`→検証を呼ぶ。独自の状態DBは作らない。

1. 対象Vault・取得元の権限・既存ジョブ・Git状態・Knowledge CompilerのCLI版を確かめる。OKF未移行なら公式の移行手順を別に一度適用する。
2. 複数の取得元はrcloneの`combine` backendで互いに異なる名前のサブフォルダへ束ね、一つの`KAFSTYLER_INGEST_SOURCE`として渡す。抽出先の同名衝突は`--apply`がVaultへの書き込み前に拒否する。
3. `rclone copy SOURCE DEST --dry-run`で更新を確認し、`--check`で形式の現状を測り、代表入力で`--apply`の初回・再実行・失敗を検証する。スクリプトは`flock`で同時実行を防ぎ、Git管理Vaultでは作業前のcleanな`main`と、成功後のローカルコミットを要求する。外部pushは行わない。
4. 既存の定期ジョブと重複しないOS起動元に切替える。取得に失敗した回を差分なしと記録しない。OrcaはAIが必要な差分のときだけ`--precheck`で起動し、実行IDと完了の検証を既存の案件へ結び付ける。Orcaの手動実行はprecheckを迂回する。
5. 固定規則で解決できない分類に限って`adjudicate`で小型モデルを独立評価する。d1-2Bの常駐は必須でなく、判断不能・生成・実装が必要な場合だけ認可済みfrontierモデルに昇格する。再試行は上限を持ち、成果を読み戻してから処理済み位置を更新する。

## VRChatを妨げないVRC Friend Connect連携

VRC Friend Connectのデータはローカルの第三者情報を含む。VRChat・SteamVR・VRC Friend Connectの稼働中は一切DBを開かず、モデルも起動しない。OSの待機時間帯にだけ、[読み取り専用の構造検査](../../scripts/vrcfriend_offline.py)を利用する。VRChat APIやゲームのプロセスに接続しない。

- **入口。** Windowsで既存のPython実行環境を明示し、`python scripts/vrcfriend_offline.py` を実行する。既定のデータルートは `%APPDATA%\VRC Friend Connect`。WSLでは `--root` でWindowsの実パスを指定する。Windowsの `tasklist.exe` にアクセスできなければ停止し、別コマンドへ無言で切り替えない。
- **停止優先。** VRChat、SteamVR、VRC Friend Connectが起動中なら `skipped`。途中で起動した場合も検査結果を破棄する。SQLiteは `mode=ro&immutable=1` でスキーマのみを読む。未チェックポイントのWAL、DB破損、依存不足は異常停止し、読み込みに失敗した状態を差分なしとみなさない。対象アプリのファイルを変更しない。
- **個人情報を持ち出さない。** 対象は公式掲載の `db_1.1.sqlite` と `db.sqlite`。行の値、フレンド名、ユーザーID、メモ、認証情報、設定、ログ本文は取得・出力しない。最初の出力はテーブル名・列名・スキーマ版のみ。生成した報告をGit管理Vaultへ無条件で同期せず、個別データの取り込みは実スキーマ、用途、保存先が確認されてから別途採否を決める。
- **小型判断モデル。** 標準動作ではLLMゼロ。候補表の用途判定が必要なときだけ、別途用意したローカルの `d1-2B` `/v1/systemone` に `--d1-endpoint http://127.0.0.1:8080/v1/systemone` で任意接続する。送るのはテーブル名・列名のみで、出力は未検証の提案。モデルを常駐させず、VR利用中にGPUを占有させない。CPUのみ・少数スレッドの実行環境で、固定規則や素の構成より有効な場合だけ採用する。候補判定がどのDBレコードを読むかの許可にはならない。

データを読み込む通常利用は、ユーザー端末で稼働停止→スキーマ確認→許可された列だけの抽出設計→別の静的評価→実機確認の順に進める。スキーマ未確認の段階で特定の友人・行動履歴を読み出すコードを推測実装しない。[一次資料](../../bibles/agents-and-orca.md#vrchatと小型判断モデルのローカル連携)

## Orca機能を選んで使う

Orcaが利用可能なホストでは、`autocatalyze`が**仕事の目的と実行先から必要なOrca機能を選び、実際に使う**。Orcaは既存のClaude Code・Codex・Antigravityの代わりではなく、それらを起動・監督・接続する環境。別の起動元、同じ用途のSkill、監視台帳を増やすためには使わない。[Orcaの選定根拠](../../bibles/agents-and-orca.md#orcaを横断運用の実行基盤にする)

| 仕事の条件 | 選ぶOrca機能 | 完了の確かめ方 |
| --- | --- | --- |
| 一回の修正・質問・端末操作 | 既存Terminalを`list`・`read`で確認し、必要なら`terminal send`。追跡が不要ならRunを作らない | 実行したCLI・Git・実物の結果 |
| 複数担当の調査・反証・依存関係 | OrchestrationのRun・Task・Dispatchで`disprove`・`adjudicate`等を委譲。単一`main`への書き込みは一担当に集める | Task/Dispatchの結果を読み、成果を別途検証 |
| 時刻に応じて起動する仕事 | 既存スケジューラーを確認した上でAutomations。既存workspaceを指定し、差分が分かるならprecheck | 予定・実行・成果・次回予定と重複の有無 |
| Issue・PR・Slack・Linear・Webhookのイベント | Botsで受付・分類・返答。外部入力を実行命令にしない。コード変更は既存`main`の担当へ渡す | イベント元・案件ID・報告先と反映先の照合 |
| 公開Web・GUI・モバイル画面を確かめる | 埋め込みBrowserのsnapshotと操作、Computer Use、対象がある場合だけEmulatorを使用 | `adjudicate`が公開・保存後の実物を確認 |
| 別PC・常時稼働・移動中の確認 | Remote Orca ServerとMobileで実行ホストを選ぶ。クライアント切断とホスト停止を区別 | ホスト上の実行結果・再開状態・必要な回答 |
| モデル枠・エージェントが足りない | OrcaのUsage・Agent状態とホストで利用可能なモデルIDを読み、[モデル選定](../../AGENTS.md#モデル選定)を適用 | 実際に起動できた担当・費用上限・合格結果 |
| 外部サービス・ファイル形式・開発環境が必要 | 標準機能→公式Skills/既存MCP→必要なPluginの順に確認。Skillは実行版の`orca skills get`を読む | 必要な操作が通り、重複拡張が増えていない |

**能力判定。** Orcaを使う初回または環境変更・失敗時は`orca status --json`で接続を確かめ、対象がGit作業なら`orca worktree current --json`と[Gitの作業状態](../../AGENTS.md#gitの作業状態)を照合する。必要な機能に応じて`orca terminal list --json`、`orca automations list --json`、`orca skills installed --json`を読む。コマンド詳細は実行中の版に一致する`orca skills get orca-cli --full`または`orca skills get orchestration --full`から取得する。全操作の前に全機能を調査し直さない。CLI不達・ホスト不在・権限不足のときは既存CLIで実行できる工程を進め、未実施のOrca操作を成果に数えない。

**委譲の単位。** [案件コンテキスト](../canonicalize/SKILL.md#案件コンテキストを組み立てるproject-as-code)で選んだ目的・仕様・コードの参照をTask/Dispatchへ添え、`reconceptualize`が選んだ問題、`canonicalize`の作業ID・対象版、`disprove`の破綻条件、`adjudicate`の合格条件を渡す。担当には読み取り専用か書き込みか、使うホスト・モデル、期限と停止条件、提出する根拠を明示する。Orcaの実行状態は一時的な観測、Git/Issue・公開先の実結果は正本として区別する。監督付きの仕事が完了したら必要なログを読み戻して`worker-release`で端末を整理する。次の起動ではOrca側の状態だけを信用せず`canonicalize`から再開する。

## Orcaで監督して実行する

OrcaからClaude Code・Codex・Antigravityを起動するときは、**[Kafstyler優先の共通規約](../../AGENTS.md#orcaなど外部実行環境との優先順位)をOrcaの既定動作より優先**し、[公式資料の採用判断](../../bibles/agents-and-orca.md#orcaでエージェントを監督する)を参照する。Orcaは実行環境と監督、`autocatalyze`は案件選定・実装・実物の合格、`canonicalize`は正本・版・再開状態を担う。

最初に[Orcaの公式Skills](../../bibles/agents-and-orca.md#orcaの拡張を選ぶ)の導入先を`orca skills installed --json`で確認し、必要なら`orca skills install --all --dry-run`で変更対象を調べる。`orchestration`は試験機能のため、実行するOrcaで有効になっていることを確認する。CLIが使えることと、Orcaの標準BotがKafstylerの規約で書き込めることは別の条件。

1. `orca status --json`、`orca worktree current --json`と[Gitの作業状態](../../AGENTS.md#gitの作業状態)で、対象が既存の`main`チェックアウトか確認する。既存作業場所から`orca agent launch --agent codex --json`で起動するか、場所を`--worktree path:<既存の絶対パス>`で指定する。Orcaが使えない場合もKafstyler単体の実行を止めない。
2. 単発の依頼は既存端末で進める。監督付きの仕事は`orca skills get orchestration --full`で実行版の仕様を読み、`orca orchestration run-create --objective "<達成条件>" --json`でRunを作り、`orca orchestration task-create --spec "<対象・権限・合格条件>" --task-title "<作業名>" --json`でTaskを作成する。Run自体はワーカーを起動しない。既存`main`の作業場所と一致し、同一リポジトリに別の書き込み担当がいない場合だけ`orca orchestration worker-start --task <taskId> --worktree current --agent codex --json`で担当を起動する。Orca Botの標準コード変更フロー、`new-child`、新規worktree作成、共有checkoutへの同時書き込みを使わない。独立した他リポジトリの作業や読み取り専用の監査は並列で実行できる。
3. Task/Dispatch IDとKafstylerの案件ID・対象コミットを対応付ける。調整中の質問には`orca orchestration ask`、Taskを止める判断には必要な場合だけDecision gateを使う。`orca orchestration check`で受信したDeliveryは全メッセージを扱ってからackする。ワーカーの`worker_done`は`taskId`・`dispatchId`・成否を照合し、`worker-read`と実物を検証する。確認後は`worker-release --dispatch <dispatchId> --json`で監督端末を整理する。再試行では新しいDispatch IDと既存作業IDを結び、古い完了通知を採用しない。完了の判定は[実装と検証](#実装と検証)に従い、Orcaの状態表示だけで確定しない。
4. コメント更新の前に既存の文面を確認する。`orca agent hooks status --json`で管理フックを切り分け、承認エラーが作業を阻害する場合は`orca agent hooks off --json`でOrca管理の状態通知を停止できる。不要なフック・重複するスケジューラー・第2の台帳は作らず、既存の起動元を切り替えるときは旧経路停止と再開の検証まで行う。

GitHub Issue・Slack・メール等の外部内容を受け取るOrca Botは、[公式Bot security](https://orca.dev/docs/bots/security)に従って`Who can ask`とイベント自動起動の範囲を分け、書き込みを伴うFull accessを初期状態のままにしない。Botの読み取り専用の問題発見結果を受け取ってから、既存`main`上の単一実行担当に渡す。No Worktreesプラグインは失敗時に通過し得るため、この規約の強制装置と見なさない。

Orca CLI、フック切替、ワーカーの起動を実行していない場合は実施済みと報告しない。


## OrcaのAutomationsとBotsを使う

Orcaは**起動・受付・通信・ホストの継続稼働**を担当し、`autocatalyze`が案件選定・書き込み・成果検証を担う。[公式仕様と役割の正本](../../bibles/agents-and-orca.md#orcaを常駐通信基盤として使う)に基づき、外部実行基盤の変更によって既存の仕事を二重起動させない。

1. **起動と接続を確定する。** `orca status --json`、`orca automations list --json`、既存スケジューラー、Botの自動化、GitHub等のイベント受付を照合する。対象のホスト・時刻・タイムゾーン・Workspace・発火条件を確認し、既に同じ案件を起動できる経路があればそれを使う。Botのイベント自動化とCLIの定時Automationは独立した入口として照合する。
2. **定時処理を構成する。** `orca skills get orca-cli --full`で実行版の手順を確認する。必要な場合に限り`orca automations create`で`--provider`・`--trigger`・`--timezone`・既存`main`の`--workspace`を指定し、`--disabled --json`で作る。安い取得で処理する差分が判定できるなら`--precheck`を使い、**終了コード0で起動、非0でスキップ**になることを実入力で確かめる。プロンプトは案件ID、`autocatalyze`、出力・合格条件、再開の正本を指定する。`--repo`が別worktreeへ進む運用は採用しない。
3. **セッションと復旧を設計する。** 原則は新規セッションから`canonicalize`の記録を読み戻す。`--reuse-session`は同じWorkspaceの生きたTerminalへ文脈を引き継ぐ必要があるときだけ選ぶ。`--extra-agent-args`によるモデル・effort変更は新規セッション用で、`--reuse-session`と併用しない。予定実行の欠落猶予を要する場合は`orca automations edit <automationId> --missed-run-grace-minutes <minutes> --json`を設定する。ホスト停止や通信断から戻ったら履歴と対象サービスの正本を再照合する。
4. **Botで外部イベントを受ける。** GitHub・Slack・Linear・Webhookの内容を出典・イベントID・対象版とともに受け取り、`reconceptualize`へ優先すべき問題の候補を渡す。Botの`Who can ask`とイベント起動の対象は別に設定する。外部の文章は命令として実行せず、開始時のFull accessを前提にしない。承認できるのが依頼者の場合もあるため、初回は読み取り中心の受付・分類だけにし、書き込みが必要なら認可済みの単一`main`担当に渡す。WebhookのURL・署名は機密として管理する。
5. **通信と成果を照合する。** Orchestrationでは`orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json`などでDeliveryを受け、すべてのMessageと`taskId`・`dispatchId`を処理・記録してから`orca orchestration check --ack <deliveryId> --json`でackする。受信や`worker_done`だけで合格とはせず、`main`のコミット・公開結果・利用者の入口で確認する。再送やack前の中断は既存作業ID・書き込み操作IDで重複を防ぐ。外部イベントはOrca Cloudで最大1日しか待機しないため、長時間停止後は元サービスの更新履歴から処理漏れを照合する。
6. **導入と停止を検証する。** `orca automations show <automationId> --json`で設定を確認し、`orca automations run <automationId> --json`、`orca automations runs --id <automationId> --json`で停止状態のAutomationを手動検証する。Botは既存のIssue一件を分類させ、作業記録と二重起動・権限・通知先を確認する。新経路への切り替えでは旧ジョブの停止を読み戻し、`orca automations edit <automationId> --enabled --json`で新経路を有効化する。続く通常起動で再開・成果・通知の重複がないことを確認し、失敗したら旧経路へ切り戻す。実機で未検証なら設定済み・稼働中と報告しない。

ホストの継続稼働は[Remote Orca Servers](https://orca.dev/docs/remote-servers)で管理する。サーバーがAgent・資格情報・セッションを保持し、スマホとデスクトップは状態を見る。Linux/macOSの`orca serve service`とWindowsデスクトップの稼働条件は異なる。Orca CLIが利用できなくても、Kafstyler共通Skillsの既存CLI運用は維持する。

## Orca Botの受付・進捗と判断待ち

既存のOrca BotsとAutomationsを棚卸しし、追加のBotを作る前に同じイベントの受付先、定時ジョブ、`Look around`、`Memory upkeep`を比較する。重複する自動実行は止める。既存の受付で足りるなら新しい司令塔Botを作らない。[役割と採用根拠](../../bibles/agents-and-orca.md#orca-botsの役割分担進捗判断待ち)

1. **入口を固定する。** 外部イベントは元サービスのURL・イベントID・対象Issue・発生時刻と合わせて受付。Botの目的は問題の発見・分類・回答であり、無条件の作業委任・書き込みではない。Bot Homeの`Needs you`、既存のTask・Issue・Automationの表示を先に使い、専用の監視DB・カスタムPlugin・独自の進捗フックを増やさない。
2. **必要な判断だけ集める。** 判断を求める前に既存の指示・権限・合格条件・実物を読み、本人しか答えられない選択だけを`Needs you`またはOrchestrationの質問へ出す。選択肢、推奨理由、影響するリポジトリ・Issue・実行ID、承認後に行う操作を短く示す。Botが提案した`Next action`や推奨ボタンを既存の権限を超える許可として扱わない。
3. **作業を進めて検証する。** 読み取り専用の調査・品質レビューは独立担当に配分し、実変更は既存`main`の単一書き手へ引き継ぐ。端末進捗とOrchestration通知は途中情報として扱い、Issueの完成条件、実コミット、利用者の入口で結果を検証する。古いDispatchからの完了通知や同じ外部イベントの再配送では処理を重複させない。
4. **止まった原因で分ける。** `waiting`は質問待ち・承認待ち・利用制限・ホスト停止を確認して判定する。再起動や枠切れでBotが止まる場合、元サービスの状態と最後の成果を再取得し、[停止と再開の契約](#常時稼働エージェントの中核)で一度だけ再開可否を判断する。観測できない状態を完了・差分なし・再開済みにしない。
5. **小さく合格させる。** 既存の一案件を使い、受付、重複イベント、人間の判断待ち、途中停止、`main`の成果確認の各経路を検証する。実ホスト未接続なら設定済みと報告せず、未実施の入口と必要な認証・接続・実機確認をIssueへ残す。正常に使えてから別Bot・複数PCへ拡大する。

## Orcaの横断運用

**構想：Kafstylerが判断と成果を統括し、Orcaが複数CLI・ホスト・画面の実行状態をまとめる。** Orcaの機能を追加すること自体を目標にせず、既存の監視・自動化・正本を再利用する。

1. **横断観測。** `orca search --query <障害語> --scope conversation --json`や既存GitHub Issue・実行履歴から、止まった仕事、繰り返す失敗、未確認の公開結果を見つける。`reconceptualize`が解く価値のある問題を選び、`canonicalize`が案件IDと最後の確認版を紐付ける。Orca Botは読み取り専用の候補発見にも利用できる。
2. **仕事の分配。** `autocatalyze`が対象リポジトリと合格条件を確定する。OrcaのRun・Task・Dispatchで独立調査を並列化し、`disprove`・`adjudicate`に異なる検証を任せる。**同一リポジトリの書き込みは一つの既存`main`チェックアウトで直列に行う。** Orca既定のBotワークフローが新しいworktreeを必要とする場合は、その書き込み経路を使わず、既存作業場所のエージェントへ渡す。
3. **実物で合格。** 変更を`main`へコミットし、必要ならOrcaの埋め込みブラウザー・ブラウザープロファイル・Computer Useで公開画面やローカルアプリを確かめる。`adjudicate`が実測で採否を判断し、`canonicalize`がコミットと検証結果を正本に残す。Orcaの`worker_done`やUIの終了表示だけでは合格にしない。
4. **継続と遠隔。** 既存の定期ジョブ・イベント通知があるならそれを優先する。Orcaの定期実行を新しく採用する場合は`--workspace`で既存の作業場所を選び、軽い`--precheck`で無変化の起動を省き、旧経路の停止と再開を検証する。複数ホストやスマホはOrcaの状態確認・回答依頼の入口として使い、ファイルの正本は増やさない。
5. **実行枠の選択。** Orcaで利用枠・起動可能なモデルとホストを確かめる。Kafstylerの[モデル選定](../../AGENTS.md#モデル選定)を優先し、候補IDが利用先で使えないなら認可された別会社の候補へ切り替える。上限・障害・未完了は既存履歴に残して次回へつなぐ。

**最初の導入単位。** 既存の1リポジトリで、読み取り専用の障害調査 → `main`での単一担当修正 → ブラウザーからの成果確認 → 次回起動での再開を実測する。別リポジトリへの同時作業は、この一連の作業が維持できると確認してから広げる。[Orcaの一次資料](../../bibles/agents-and-orca.md#orcaを横断運用の実行基盤にする)

## 一件を合格まで進める

Claude Code・Codexで `/goal` が使える場合は、`autocatalyze` の手順、作業台帳の参照先、利用者の入口で確かめる合格条件、実行上限を渡し、目標の状態を確認する。

```text
/goal autocatalyzeを使い、作業台帳の案件42を公開URLで指定版が読めるまで進める。30分で合格しなければ、最後に確認した結果と次の操作を台帳に記録する。
```

即座に進められる工程は現在のセッションで実行する。外部の変化を待つ段階では[起動方法](#常駐エージェントと定期実行)を選び直す。別の起動手段に引き継いだら元の継続目標を停止して状態を確認する。`/goal` が使えない環境でも着手し、合格条件まで進められる範囲と再開の入口を台帳に残す。

## Claude Codeの /loop 連携

短時間の見守りを任された場合に、[公式の `/loop`](../../bibles/agents-and-orca.md#claude-codeのloop)を使う。対象、間隔、止める条件を渡す。

```text
/loop 5m /kafstyler:autocatalyze 配布の反映を待つ。公開URLで指定した版を読めたら終了する
```

1. **登録と初回実行を確認する。** 登録時の表示または `CronList` でジョブIDを確認する。最初の予定実行で `kafstyler:autocatalyze` が呼び出され、確認対象の状態を読み戻したことを確かめる。呼び出せない場合は、スキルの利用を許可する設定を確認する。各回は同じジョブと案件を引き継ぐ。セッションを再開したときは、台帳と実行中のジョブを照合してから監視を戻す。`/loop` が使えない場合は、現在のセッションで可能な確認を行い、見守りを継続できる範囲を伝える。
2. **不要になった監視を解除する。** 合格・中止、または回答やイベントで再開する手段へ引き継いで見守りが不要になったときは、`CronDelete` で対象IDを解除し、`CronList` で確認する。解除に失敗した場合はジョブIDと解除操作を報告する。

## Claude Agent SDKでの実装

Claudeで動くエージェントを実装する場合は、[実行方式の比較](../../bibles/agents-and-orca.md#claude-agent-sdk)で運用に合う方式を選ぶ。Agent SDKでKafstylerを使う場合は、`plugins` に `{ type: "local", path: ... }` を指定し、`path` に使う版のプラグインのルートを渡す。

起動時の `init` メッセージで、`plugins` に `kafstyler`、`skills` に使う `kafstyler:<名前>` があることを確かめる。`allowed_tools`（TypeScriptでは `allowedTools`）はツールを事前承認する。禁止するツールや操作は `disallowed_tools`（`disallowedTools`）などで設定する。アプリの入口から、通常の依頼が完了し、禁止した操作が拒否されることを確かめる。

## Antigravity CLIでレビューする

別のエージェントから Antigravity CLI にレビューを頼む場合は、[配布版の導入](../../README.md)と[公式仕様](../../bibles/agents-and-orca.md#antigravity-cliの配布と実行)を確認する。ジョブを実行する環境とユーザーで認証し、`agy models` で使えるモデルIDを確かめる。レビュー対象、求める指摘と根拠、変更してよい範囲を依頼に含める。入力は、その認証先に送る許可がある資料に絞る。

秘密のないディレクトリで、確認済みのモデルIDを `REVIEW_MODEL` に設定して試す例。

```sh
agy -p "文字列 antigravity を逆順にし、結果だけ返して。" --model "$REVIEW_MODEL" --output-format json --print-timeout 5m
```

疎通の合格条件は終了コード `0`、JSONの `status` が `SUCCESS`、`response` が `ytivargitna`。実作業では標準エラーも保持する。承認が必要なツール操作がヘッドレス実行で拒否されても、終了コード `0` で続く場合がある。必要な操作が行われたことを確認し、指摘を対象の行や実際の操作結果と突き合わせる。

## 実装と検証

1. **現状と合格条件を確認する。** [Gitの作業状態](../../AGENTS.md#gitの作業状態)に従い、着手前にworktree、ブランチ、未コミット差分を照合する。既存の作業を上書きせず、プロジェクトの現状、利用者が使う入口、合格条件を確認する。目的が曖昧なら [reconceptualize](../reconceptualize/SKILL.md) を、評価が必要なら [adjudicate](../adjudicate/SKILL.md) を使う。進行中のIssueやPRがあればその作業を引き継ぐ。データ構造の設計が必要なら、[`kafstyler:canonicalize`](../canonicalize/SKILL.md) を呼ぶ。答える問い、実データの例、変更範囲を渡し、結果を実装に使う。作業を分けるときは、各単位の担当、成果物、合格条件を決める。人間による認証が必要な場合は、事前確認を済ませ、必要な操作と再開条件を伝える。
2. **変更する範囲を絞る。** 実際の障害を確認し、役割を終えた経路や重複を除く。標準の道具と公式APIを使い、依頼に必要な変更単位を選ぶ。フロントエンドではプロジェクトのデザイン規則に従う。KAFKA2306のWeb UIでは、[かふかのデザインパターン](../../bibles/design-and-ui.md#かふかのデザインパターン)から設計・同期の手順を開き、操作パターンと共通部品を選ぶ。共有デザインの導入・更新を含む場合は採用版を固定し、正本の手順で同期と適合確認を行う。設計案の検討には、利用できる場合は `demolab:gemini-frontend-design` を使う。[目標設定](../reconceptualize/SKILL.md)で決めた操作を、利用者が使う画面幅で入口から完了まで確かめる。[DemoLabの公式手順](https://github.com/google-gemini/demolab#claude-code)
3. **置き換え候補を検証する。** 現行方式の前提や置き換え候補の反証が依頼に含まれる場合は、[`kafstyler:disprove`](../disprove/SKILL.md) を呼ぶ。検証する前提、観測された問題、置き換えの条件を渡す。手法を置き換える場合は、[`kafstyler:adjudicate`](../adjudicate/SKILL.md) を呼び、現行と候補、共通の入力、設計前に固定した評価を渡す。評価で合格し、品質や運用工数が改善し、保守と検証の根拠がある候補を採用する。通常の入口で移行後の動作を確認したら、[`kafstyler:decommission`](../decommission/SKILL.md) を呼び、置き換えた旧実装、整理の範囲、移行時の評価結果を渡す。
4. **制作環境で出力を確かめる。** ComfyUIでは最初に[Workflow選定と採用の基準](../../bibles/design-and-ui.md#comfyuiのワークフロー選定)を読み、制作目的に合う候補と採用条件を確認する。公式テンプレートは `Workflow → Browse Workflow Templates` から開く。候補の版と必要モデルを記録し、制作環境で出力を確かめる。[Unity・VRChat制作](../../bibles/dev-infra-and-3d.md#ユニティとvrchatの制作ツール)では用途に合うツールを選び、対象プロジェクトで確かめる。シェルでは一つのコマンドに一つの仕事を任せ、標準入出力でつなぐ。
5. **実物に検証をかける。** 利用者の入口から実物を検証する。既存テストと合格条件を使い、未確認は未確認として報告する。新しいワークフロー、CI、テスト、スクリプト、フックは具体的な失敗を検出するか、実測した繰り返し作業を減らす場合に加える。整理では重複した確認を取り除き、削減した件数や工数を測る。
   - [実物を使う検証](../../bibles/mission-eval-writing.md#claude-codeの検証)では、ローカルで動かせる安価な検査から始める。続けて、対象を起動し、普段の入口に代表入力を与え、最後に表示や保存先を読み戻す。失敗時は対象の版、止まった操作、期待した結果、ログや画面の観測を残す。繰り返し使う起動と確認手順は対象に近い既存の文書やスキルへ置く。
   - 新しい必須チェックを作る場合は、まず条件に該当した結果を記録し、誤検知を確かめてから必須化を判断する。失敗したら原因を調べて修正し、その影響範囲を再検証する。解消できないときは再現手順、試した修正と観測、判断が必要な点を残す。記録した見逃しのうち、差分と再現手順で判定できるものは既存の検証やレビュー手順の改善候補にする。
6. **配布して利用者の入口から確認する。** 配布に重大なリスクがある場合は [disprove](../disprove/SKILL.md) で反例を調べる。変更後の実物、普段の入口、合格条件と検証結果を渡す。通常利用、途中失敗、再試行で成果が成り立つかを確かめ、確認できた重大な欠陥を直し、同じ自動判定で合格を確かめてから対象リポジトリの規約に従って配布する。Kafstylerでは[Gitの作業状態](../../AGENTS.md#gitの作業状態)に従い、1ワークツリー・`main` 1ブランチで変更単位ごとに逐次コミットする。終了前に未コミット差分をゼロにし、コミットと未完了工程の再開条件を読み戻す。既存のPRや作業ブランチが残っていれば必要な変更を確認・統合し、後片付けまで完了する。公開する変更では、対象コミットから生成した成果物を、公開先が実際に返したファイルや版と照合する。その公開先で利用者の操作を最後まで通す。成果物が古ければビルド設定と配信先を調べる。

技術白書の依頼では [didactizationの白書手順](../didactization/SKILL.md#技術白書を構成する) を執筆の入口にし、`reconceptualize` の採否条件、`canonicalize` の出典・版、`disprove` の反例、`adjudicate` の比較結果を引き継いで原稿を更新する。`decommission` が整理した旧稿・重複参照を確認し、公開した版で結論と根拠のリンクを読み戻す。継続案件では新しい一次資料や実測が結論に影響したときだけ更新し、次回へ引き継ぐ。

動作する変更と根拠を届ける。[共通の出力手順](../../AGENTS.md)に従い、確かめた試用の入口を成果とともに渡す。実行を妨げる問題が残る場合は次の作業を示す。
