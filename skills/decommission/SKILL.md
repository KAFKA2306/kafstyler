# 廃止と統合

削除件数や文字数を成果にしない。利用者の成果を保ちながら運用経路と保守負担を減らす。

1. 目的、利用経路、読取・書込・呼出元、依存、保持データを特定する。不要、重複、外部実装で代替可能、必要、判断不能を区別する。名前やサイズだけで削除しない。
2. 現状維持、統合、標準機能・外部CLIへの移管、廃止を比較する。必要な能力を後継が担えるか、旧方式でしか得られない成果や判断がないかを設計時に整理する。根拠の弱い重大変更は [disprove](../disprove/SKILL.md) または [adjudicate](../adjudicate/SKILL.md) の判断を使う。
3. [canonicalize](../canonicalize/SKILL.md) と正本を決め、旧箇所にしかない事実、適用条件、ID、出典、履歴、利用者データを移す。固有の判断基準・手順を重複説明と取り違えない。
4. 認可範囲で後継へ切り替え、不要な旧実装・設定・ジョブ・互換ラッパー・文書・参照を同じ変更で廃止する。公開済み旧リンクは必要な場合だけ案内を残す。判断不能な項目と他者の変更は保持する。
5. 廃止・統合・保持した対象、後継入口、残る問題を返す。調査だけなら削除せず候補を返す。

## 領域別の整理

- 定期処理：取得・差分・計算をCLIや数式へ、意味判断だけをLLMへ移す。二重反映・通知を避け、処理済み位置を引き継ぐ。既存起動元を統合し不要な常駐・同期・台帳を増やさない。
- 文書・Vault：正本・後継への検索経路を維持し、同名の異なる対象を統合しない。旧稿にだけある出典・測定条件・適用限界を移す。
- Skill：発動条件、専門判断、手順、出力、他Skillへの受け渡しを保持する。共通規約の再掲と製品固有の操作説明だけを該当正本へ寄せる。低頻度の詳細は必要な場合だけSkill内の references/ へ置く。
- 開発：未コミット・未追跡の内容も扱うが他者の変更を破棄しない。使われる資源・再取得不能データを保持し、Git履歴を別台帳に転記しない。
