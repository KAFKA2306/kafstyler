# 不要なファイル・コード・文章の削除

依頼の範囲で、不要と確認できたファイルや処理を取り除く。調査・提案のみの依頼では削除候補と根拠を示す。利用者が普段の入口から必要な操作を続けられ、仕様・実装・設定・文書が一致する状態を保つ。

[整理の手順](#整理の手順) · [削除後の確認](#削除後の確認)

任意の出力で人が読む文章には[imozの執筆・推敲ルール](../../BIBLES.md#imozの日本語編集)を適用する。[出力の共通基準](../../MISSION.md#出力の共通基準)

## 整理の手順

着手前に、かふかのZenn記事を3本読み、対象に当てはまる整理基準を選ぶ。

- [なぜAIに任せるほど、あなたのコードは複雑になるのか](../../BIBLES.md#aiが増やす判断箇所) 重複する指示・検証・状態・分岐を洗い出し、削除後も機能・正しさ・必要な証拠が揃うかを確かめる。
- [AIに同じ指示を繰り返すのをやめた。Issue駆動開発という最小運用](../../BIBLES.md#issue駆動開発) 終わった変更の経緯をIssueに残し、現在の仕様として必要な記述を正本に集約する。
- [AIを「過保護」にするな。スタックトレースを聖典とする開発規律 "Crash-Driven Development"](../../BIBLES.md#失敗原因が見える実装) 障害の原因を隠す広すぎる例外捕捉やフォールバックを見直し、根本原因を観測できる形にする。

1. **整理後の利用場面を決める。** [登大遊「論理的思考の放棄」](../../BIBLES.md#登大遊の論理的思考)を読み、整理後に利用者が普段の入口からどの操作をして、何を得られればよいかを先に思い描く。同じ入口で現状の挙動と入出力を確かめ、余分に感じる手順や、同じ役割に見える文書・機能を削除候補に挙げる。候補を外してよいかは手順3で確かめる。
   - 範囲指定がなければ、プロジェクトのルート直下から始める。Gitでは `git rev-parse --show-toplevel` でルートを特定する。ルートで `find . -mindepth 1 -maxdepth 1 ! -name .git -print0` などを使い、隠し項目、未追跡・無視対象、空のディレクトリも含めて実際の項目を列挙する。`git status --short --ignored` と `git ls-files` で追跡状態、配布設定やドキュメントで仕様・データの正本を確認する。KAFKA2306のWeb UIでは、[かふかのデザインパターン](../../BIBLES.md#かふかのデザインパターン)から設計・同期の手順を開き、共通部品やトークンと重複する利用側の定義を確認する。
2. **削除候補を洗い出す。** 用途が分からない、使われていない、または最近の利用を確認できないファイルやディレクトリを削除候補に挙げる。利用の時期は取得できる実行記録と、その操作の実施周期で判断する。最終更新日は変更時期の手がかりとして使う。正本と重複する文書や設定、利用先が現行版に切り替わった旧版、役目を終えた作業メモや一時出力、配布に使わず再生成できるファイル、使われない資産・コード・ラッパー、同じ確認を繰り返すスクリプト・テスト・CIを探す。同じ役割のフォルダは既存の管理先に統合する。既存の[評価結果](../adjudicate/SKILL.md)も使い、置き換えが済んだか確かめる。ファイル内では、結論の繰り返し、判断に使わないバッジ、未使用のプレースホルダー、読者の判断や操作に不要な作業説明を削る。一つのプログラムに一つの仕事を持たせ、必要に応じて標準入出力でつなぐ。
   - 定期・イベント処理では実行記録から、同じ取得・照合・集計、本文の全件再読込、重複する出力先、完了だけを伝える通知を探す。情報源の更新周期と利用者が待てる時間を確かめ、同じ取得や処理をまとめる。定期実行が不要な処理は、必要になったときだけ起動する。用途が同じ出力は正本に集め、利用者が対応する項目を普段の入口に出す。
3. **候補の利用経路を調べる。** 候補ごとに、移行先の正本、再生成の手順、または用途を終えた根拠を確かめ、普段の入口から使われているかを調べる。文字列検索に加え、既定のファイル名による自動検出、動的読み込み、ファイル名のパターン指定（glob）、ビルド・配布設定、CI・定期実行、手動の手順、公開パスからの利用も確認する。ディレクトリを丸ごと削る判断では配下の項目まで確認する。必要な項目があればディレクトリを残し、その中で不要と確認できたものだけを削る。シンボリックリンクやマウントを経由して調査範囲を広げない。
   - 文書・データの正本、メタデータ、保存形式、入出力の契約に影響する候補は、編集・削除の判断前に [canonicalizeとの連携手順](../canonicalize/SKILL.md#正本の移行と旧版の整理)を使う。`canonicalize` から条件を受け取っていればそれを使う。移行と利用経路の切り替えを確認してから、削除または後継への案内を判断する。条件を確かめられない候補は残し、他の整理を進める。
   - 未コミット・未追跡・無視対象も調査から除外しない。他者の変更を含め、内容と利用経路を確認し、必要な変更は保持してコミットする。不要と判定できる生成物は削除する。再取得できないデータや必要性を判定できない項目は残し、候補のパス、確認できなかった理由と次に見る利用経路を記録する。他の候補で整理を続ける。
   - 削除候補の根拠、移行先の正本、残す入口を [`kafstyler:disprove`](../disprove/SKILL.md) に渡す。判断が難しい候補から確認する。独立したレビューで判断を要する箇所が残る場合も、確かめた候補の整理を進める。
4. **必要な内容を移して整理する。** 削除する箇所にだけある事実、指示、適用条件は正本へ移す。不要と確認できた項目はパスを指定して削除し、使われていない空のディレクトリも片づける。インポート、リンク、設定、呼び出し元は同じ変更で更新する。Gitでたどれる旧版や完了済みの経緯は履歴で参照する。必要なファイルは件数目標のために削らない。
   - 定期処理をまとめるときは、取得・重複判定・計算・期限判定をコードや数式で先に行う。本文とは別に、IDと更新を識別できる値（版など）を保持する。その情報で差分を絞り、判断や要約が必要な分だけをLLMに渡す。必要な取得がすべて成功し、差分がなければLLM呼び出しも定型通知も省く。取得失敗と処理済みの記録は[常駐運用の手順](../autocatalyze/SKILL.md#常駐エージェントと定期実行)に従って扱う。旧方式の起動は、手順5の切り替え前の照合に合格してから止める。
   - 整理によってタイトル・見出し・用語を変更したら、[`kafstyler:humanizer`](../humanizer/SKILL.md#タイトル見出し用語の見直し) に変更箇所、正本、読者を渡す。推敲した文言を反映し、更新した参照先も確かめる。
   - 検査を減らす場合は、[検証手順の評価](../adjudicate/SKILL.md#検証手順の評価)を使い、残す確認が既知の失敗を再現して拾い、正常例を通すことを確かめる。不安定な検査は失敗条件を調べ、修正か廃止の根拠を残す。[Claude Codeチームの検証原則](../../BIBLES.md#claude-codeの検証)

### 削除後の確認

5. **残した入口で動作を確かめる。** 削除対象が実際に消えたことを差分とファイルの有無で確かめ、残した入口を同じ入力で実行する。仕様・実装・設定・文書を正本に照合し、参照切れや挙動の変化があれば直すか、問題を起こした削除を戻す。比較が必要で同じ確認の結果がまだなければ、[`kafstyler:adjudicate`](../adjudicate/SKILL.md) に削除前の入力と観測結果、入口、合格条件、変更範囲を渡す。削除したパスと件数、確認結果、保留の理由を記録する。削除がゼロ件なら、調べた範囲と残した理由を記録する。
   - **定期処理の切り替え前。** 同じ入力で新旧の結果を比べ、比較中の二重反映と二重通知を避ける。再送、同じIDの更新、取得失敗を試し、必要な情報が許容時間内に普段の入口へ一度だけ届くことを確かめる。最後に確認した成果と入力の版、処理済みの位置、次の起動条件を同じ作業台帳から読み、新方式で再開できることと切り戻せることを確かめる。[定期実行の評価](../adjudicate/SKILL.md#定期実行と再開の評価)に従い、起動回数、LLM呼び出し、読み込み量、確認先の数から変更に効く指標を測る。
   - **定期処理の切り替え後。** 旧方式の停止を設定から読み戻す。次回の通常起動で新方式だけが動作し、設定条件を満たす成果と通知がそれぞれ一度だけ届くことを実行履歴と普段の入口から確かめる。失敗したら確認済みの切り戻し手順を使い、同じ作業台帳へ結果を記す。旧方式の設定やファイルは、その役割を新方式で引き継げたことを確かめてから削除する。
   - `canonicalize` と連携した候補は、整理後の正本と利用経路を受け取った検証条件で確かめ、削除・案内・保留の結果とともに元の作業へ戻す。文書は [OKFの確認手順](../canonicalize/SKILL.md#okfに沿って文書を更新確認する)で種別・タグの検索と、出典・後継への参照も確かめる。
   - 検証後に [共通のコミット手順](../../AGENTS.md#ブランチとコミット)に従い、必要な変更をコミットする。保留した項目でGitの状態を解消できない場合は、残ったパスと理由を作業台帳に記録する。
